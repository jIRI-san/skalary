## Decisions

- **Packaging:** a plugin **family** — new `architecture-notes` plugin (notes + skill + thin prompts) and new `architecture-tests` plugin (runner + schema + config + fixtures). Integration into the existing `create-implementation-plan` and `continue-implementation` plugins is **surgical edits**, not new plugins. Each installs/versions independently (per plugin-registry.design.md).
- **Parallel notes tier:** a new `docs/architecture-notes/` tier with its own `.architecture-notes.md` index, sitting **above** design notes. `.github/copilot-instructions.md` loads **both** indexes. Design notes stay implementation-level; arch notes are interface-level, contract-level.
- **Skill-first UX:** the primary experience is a `SKILL.md` workflow fully usable standalone in CLI (create / update / review arch notes + contracts). Prompts `/can` + `/uan` are **thin shortcut wrappers** that defer into the skill and carry no logic. This is a deliberate contrast with the legacy prompts-only `design-notes` plugin (migrating `design-notes` to skill-first is a tracked non-goal).
- **Multi-modal contracts:** a contract may be authored as declarative structural rules, prose component descriptions, real C#/TS interface stubs, or any mix. The arch note is the single human-owned source of truth; agents derive the concrete framework tests, which the human reviews and locks.
- **Contract maturity:** every contract has an enforcement level — `locked` (arch tests **block**) or `draft`/`provisional` (**warn-only**). Reuses the existing warn-vs-block evidence pattern. The system grows one `locked` contract at a time; `cip`'s no-TBD applies only within the current plan's scope. See [decisions/enforcement-model.md](decisions/enforcement-model.md).
- **Hybrid enforcement + failure taxonomy:** deterministic frameworks (NetArchTest for C#, ts-arch for TS) hard-gate via native toolchains behind a pluggable adapter interface; an LLM semantic layer runs behind a **semantic-eval provider seam** (see below) and stays **advisory in the gate always** (never hard-blocks CI). Every check yields one of a fixed **failure taxonomy** — `pass` · `fail` (ran, violated) · `skip-absent-toolchain` · `error` (run failed / network). **Only a deterministic `fail` on a `locked` contract blocks**; `skip` never counts as pass for a locked contract (no false-green) and never as fail for env-portability — it surfaces as an explicit blocked/unrun state the gate reports. Arch-note text is untrusted input to any LLM step. See [decisions/enforcement-model.md](decisions/enforcement-model.md).
- **Eval-backend abstraction (Waza-ready):** the LLM semantic layer does **not** hard-depend on the repo's current custom eval harness. It targets a thin **semantic-eval provider interface** with a default `custom` provider (today's `.eval.config.json` / `Test-Evals.ps1` model) and a planned `waza` provider (YAML `eval.yaml`, LLM-as-judge graders, `mock`/`copilot-sdk` executors — https://microsoft.github.io/waza/). Swapping backends is an adapter + config change, not a runner rewrite. This mirrors the deterministic-framework adapter pattern. See [decisions/enforcement-model.md](decisions/enforcement-model.md).
- **Execution boundary (no toolchain in the CI gate):** the runner that shells to `dotnet test`/`npm`/`vitest` runs **only inside `/ci` implementation/crosscheck**, opt-in like the eval harness's `-IncludeLlm`, with `npm ci --ignore-scripts` / `dotnet restore --locked-mode`. `scripts/validate.ps1` and `npm test` stay **dependency-free/structural** (they must run identically on the Windows host and the autopilot Linux container) — they verify the runner's **receipt** by pure parsing, never execute toolchains. This preserves the plugin-evals boundary (real execution stays in the eval harness, out of the CI gate).
- **Trust anchor = git history + human commit (not crypto):** the threat model is *untrusted plan/contract text forging a pass* — **not** defending against a component we already trust to run the tests. You cannot cryptographically defend against the runner that also produces receipts (a compromised runner just signs the forgery), so we do not add HMAC/signing infra. Instead the anchor is the same one `evidence.md` already uses: **the human-authored commit + git review**. The receipt proves *integrity + freshness* ("a real run happened at this tree-state, here is its verdict"), not anti-forgery; a human reviewing/committing the `locked` contract **and** its receipt in the same PR is the tamper-evidence. See [decisions/enforcement-model.md](decisions/enforcement-model.md).
- **Lock-before-execute (human-commit bound):** agents may *derive/draft* framework test code from contracts, but **only human-reviewed, `locked` test bodies are ever compiled or executed** by an adapter. `maturity: locked` is honored **only when the `draft→locked` promotion landed in a human-authored/reviewed commit** — autopilot/autonomous `/ci` is **forbidden** from self-promoting `draft→locked` (an agent may *propose* a lock; a human merges it). A **body-level hash** (`lockedBodySha256`) is re-checked by the runner immediately before execution, so an agent cannot mutate the executable body of an already-`locked` contract and have it run. Deriving and executing are separate stages with a human gate between them.
- **`arch:` marker = pure-parse of an integrity/freshness receipt:** `Test-Plan.ps1` stays a pure parser (its invariant is *no dynamic command execution from plan content*). The `/ci` runner produces a receipt (contract-id + **tree/content-hash** bound, carrying the taxonomy verdict — schema `arch-test-receipt.schema.json`, mirroring `Build-EvidenceReceipt`/`evidence.md`, committed alongside `evidence.md`). `arch:<ContractId>` verifies by pure-parsing that receipt — never by executing tests. Freshness binds to the **tree/content hash of contract + target sources** (not raw `HEAD` equality, which would self-invalidate the moment the receipt is committed); the recorded SHA is treated as the parent commit. `Get-TypedEvidenceMarkers` is extended to extract `arch:`, and an **unknown/unrecognized typed-marker prefix fails loud (unrun/error), never silently drops** — so a stale bundle blocks rather than false-greens.
- **Failure taxonomy × maturity gate mapping (explicit):** the full matrix is specified, not left to implementers. For a **`locked`** contract, **only** a deterministic `pass` greens; `fail`, `error`, **and** `skip-absent-toolchain` are all **non-passing / unrun-required** (block finalization, never green) — an attacker or flaky harness must not be able to convert a would-be `fail` into an `error` and ship. For **`draft`/`provisional`**, every non-`pass` outcome is warn-only. LLM semantic verdicts are advisory regardless of maturity. See [decisions/enforcement-model.md](decisions/enforcement-model.md).
- **Dual representation:** the AI-optimized arch notes + ADRs are the source of truth (terse, auto-loaded); a separate human-readable doc (Mermaid, links, prose, hierarchy-capable) is **generated on every arch change** and **excluded from AI auto-load** to protect context budget. Generation has a **concrete trigger** (the `/uan` update flow / a validation step) and the staleness gate binds a **content hash of the contract sources into the generated doc** (not file mtimes), so drift is deterministically detectable. See [decisions/dual-representation.md](decisions/dual-representation.md).
- **ADR feedback loop + untrusted-content containment:** decisions made during `/cip` and `/ci` land as ADR entries under `docs/architecture-notes/`, harvested at plan finalization via `/uan`, and auto-loaded by `/cip` + `/ci` on the next run. Harvested/auto-loaded arch text is untrusted (brownfield harvest scans an untrusted repo), so harvested content is **gated behind human review before it becomes auto-loadable**. **Containment honesty:** auto-load works by `copilot-instructions.md` telling the agent to read the index + notes *directly* into context — there is **no wrapping/fencing step on that path** (the GUID-fence machinery lives only in the LLM semantic-eval *provider* invocation). The containment story therefore rests on the **human-review-before-auto-load gate + the terse template-constrained format**, not on runtime fencing of index-loaded content.
- **ADR lifecycle (bounded auto-load):** ADRs accumulate monotonically, and terse-format bounds per-note verbosity but not note *count*. Only **active** decisions stay in the auto-loaded `.architecture-notes.md` tier; **superseded/accepted** ADRs are summarized into the relevant contract or moved to a **non-indexed archive** by the `/uan` harvest flow, bounding the always-on token cost the two-index divergence is priced against.
- **Seeding flows:** greenfield init always runs a short seeding interview (1–2 `draft` contracts + human-doc skeleton); brownfield runs harvest → draft (all warn-only) → **human review/lock** → auto-loadable. Both converge on the same `/cip`-driven evolution loop. See [decisions/seeding-flows.md](decisions/seeding-flows.md).
- **Two-index divergence (intentional):** `copilot-instructions.md` loads **both** `.design-notes.md` and `.architecture-notes.md`. This is a deliberate divergence from the repo's single-index strategy — chosen because always-on architecture context materially improves the agent's understanding when querying complex codebases, and the per-run token cost is accepted. The divergence is documented in `copilot-customizations.design.md` so it is owned, not silent drift.
- **Supply-chain integrity + honest containment:** fixtures ship **committed lockfiles + integrity hashes**, restore/install **frozen with lifecycle scripts disabled**, and pin adapter framework versions in manifests. **`--ignore-scripts` is not runtime containment** — it disables install-lifecycle scripts, but `vitest`/`dotnet test` still execute third-party framework/dev-dep code (and MSBuild targets from restored NuGet packages) in-process at test time. True containment requires the **container backend**, which `plugin-evals.design.md` marks **reserved/unimplemented**. This plan does **not** build that backend; until it exists, real fixture runs execute in the documented **non-containing sandbox**, and the plan gates/labels real runs behind that caveat rather than claiming containment.
- **Script-bundling obligations + runner ownership:** the arch-tests runner's **canonical source lives at `scripts/skalary/Invoke-ArchTests.ps1`** (the single source of truth the bundling model requires), so `Sync-PluginScripts.ps1` bundles it into ci/cip like every other shared script — a plugin-owned canonical home would create a second source of truth the drift gate can't cover. Editing `PlanEvidence.psm1`/`PlanState.psm1` and adding the `arch:` marker grammar patch-bumps **every** bundling plugin, requires re-running `Sync-PluginScripts.ps1` + rebuilding `registry.json`, and updating `plan-workflow.design.md` + the cip/ci assets **in the same phase** as the grammar change (Phase 6), per plugin-registry policy.
- **Schema delivery (scaffold-on-init):** plugin installation is confined to `.github/`, so root-level `schemas/*.json` cannot be written by an installer. Schemas therefore ship as **plugin assets** under `.github/skills/<skill>/assets/schemas/` and are **scaffolded/copied to `schemas/` on init with no-overwrite semantics** (same pattern as design-note tier scaffolding) — otherwise the `file:schemas/...#exists` criteria would pass in skalary but ship schemas that never install in consumer repos.
- **Dogfooding:** skalary has no C#/TS, so the deterministic runner is validated against minimal C#/TS **fixture projects** (with intentional violations) shipped under the `architecture-tests` plugin evals, run in the container backend. The `arch:` marker itself is proven first with a plain `test:` marker (skalary has no locked C#/TS contract to satisfy a blocking `arch:` gate); `arch:contract-maturity` is dogfooded separately, not used to bootstrap its own implementation. Skalary otherwise dogfoods only the notes tier + LLM/convention checks.
- **Phase budget:** Phase 4 is the heaviest, riskiest phase — **8 points** (4.1 `L`=3 + 4.2 `L`=3 + 4.3 `M`=2: plugin + receipt schema + C# adapter + lock gate + real fixture run) — and Phase 5 is 7 points. Both exceed the hardcoded advisory cap of 6. The cap lives in `Test-Plan.ps1` and is **not** self-grantable; these are **warn-only, non-blocking** and explicitly acknowledged (not implying a configurable cap). Phase 4's weight is the honest signal that it carries the security-critical receipt + lock-gate machinery.
