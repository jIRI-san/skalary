> Retires the bespoke **Tier-2 LLM** eval backend (`tests/evals/EvalLlm.psm1` — sandbox clone, JSON-contract judge, transcript capture) and re-implements the LLM behavioral tier on **[waza](https://microsoft.github.io/waza/)** (Microsoft's Go CLI: `eval.yaml` specs, typed graders, per-task workspaces, trials/stats, `waza compare`, adversarial packs). **Tier-1 structural/contract evals stay exactly as-is** (`scripts/skalary/Test-Evals.ps1` + `tests/evals/EvalCommon.psm1` + per-plugin `*.Tests.ps1`, always-on, model-free, out of the CI gate). A **proven PoC** (`tests/evals/waza-poc/`, cr + 2 cases, 2/2 green against the real `plugins/code-review/agents/cr.agent.md`) is promoted to the shipped convention. Migrates the **9 in-scope LLM cases across 5 artifacts** — `autopilot`(1), `cr`(2), `dr`(2), `ci`(2), `cip`(2) — and **excludes the 3 `design-notes` prompt cases** (copilot CLI has no prompt executor) until a deferred prompt→skill workstream. Adds a **single pinned, explicit-approval tool bootstrap** (`Ensure-EvalTools.ps1` + `tools/eval-tools.psd1` manifest) as the one place all eval tooling (waza, gh) is provisioned on first run, and a **gh-CLI-primary token resolver** (`Resolve-EvalToken.ps1`) that sources a Copilot token seamlessly (OAuth auto-refresh — solves the corp 7-day PAT cap) with Cred-Manager fallback. **Local dev is the only target for Phases 1–2**; ADO CI enablement (vendored binary / offline path / org-secret token) and the prompt→skill conversion are scoped as later phases with explicit corp-constraint gates.

## Decisions
<!-- Key decisions made during planning — one bullet per decision -->
- **Keep Tier-1, swap only the Tier-2 backend.** `Test-Evals.ps1`/`EvalCommon.psm1`/per-plugin `*.Tests.ps1` are untouched and remain the always-on, model-free, no-auth structural gate (`npm run eval`). Only `EvalLlm.psm1` (the LLM backend: sandbox clone + JSON judge + transcript capture) is retired, replaced by waza. `npm run eval:llm` becomes the opt-in Tier-2 entry point (mirrors the old `-IncludeLlm`), never wired into `validate.ps1`/`npm test`.
- **waza is a pinned native binary, not an npm/go dependency.** waza is **not** on npm (the npm `waza` package is an unrelated 0.0.0 stub) and its binary ships git-LFS artifacts so `go install` is unsupported (source build needs Go 1.26+). We pin a release version (PoC: `0.38.0`) and resolve/download the exact asset with checksum verification — the stock `install.ps1`/`install.sh` pull **latest** and are therefore **not** used as-is. Treat waza as replaceable: eval cases stay portable YAML data so a future switch is cheap.
- **One tool bootstrap, pinned, explicit-approval installs/upgrades (no silent drift).** `scripts/skalary/Ensure-EvalTools.ps1` is the ONLY place eval tooling is provisioned; `tools/eval-tools.psd1` is the single source of truth for every tool + pinned version + install method + optional offline path. Missing tool → clear message (tool + pinned version + source) + **explicit approval** (interactive prompt, or `-Approve`/`WAZA_EVAL_APPROVE_INSTALL=1` for non-interactive). Present-but-older → run as-is, never auto-change. Newer-than-pin is surfaced only via opt-in `--check-updates` and, on approval, **bumps the pin in the manifest** so every upgrade is a reviewable diff. Downloads are checksum-verified. Missing/declined tool → actionable **skip**, not a hard failure.
- **Auth = seamless token SOURCING, gh CLI primary (AKV is out).** waza's embedded copilot-sdk **requires** `COPILOT_GITHUB_TOKEN`/`GH_TOKEN`; it does not reuse interactive `copilot login`, and copilot CLI emits no token. AKV is excluded for corp (no local auth; MSI/app + vnet only). gh CLI **can** be enforced, so `gh auth token` is the PRIMARY source (OAuth auto-refresh — no weekly PAT regen). `Resolve-EvalToken.ps1` precedence (skip-not-error): (1) `gh auth token`; (2) ambient `COPILOT_GITHUB_TOKEN`/`GH_TOKEN` (CI/override); (3) Cred-Manager targets `copilot-eval` → `copilot-autopilot` (reuses the token autopilot maintains); (4) none → actionable skip pointing at `gh auth login`. On success, set the token into env for the waza **child process only**.
- **gh-token Copilot-entitlement is a Phase-1 validation GATE.** Unverified on the planning box (no gh installed): a standard `gh auth token` OAuth token may or may not carry the Copilot entitlement copilot-sdk accepts (depends on corp GitHub app/SSO). Phase 1 confirms this before committing gh as the single seamless path. If entitled → gh everywhere, PAT/Cred-Manager pure fallback. If not → keep Cred-Manager `copilot-eval` PAT as the real source; document which orgs work.
- **Per-plugin layout co-locates waza with existing evals.** `plugins/<name>/evals/waza/{eval.yaml, tasks/*.yaml, fixtures/*}` sits beside the unchanged Tier-1 `*.Tests.ps1`. `eval.yaml` `skill:` targets the artifact's frontmatter **name**; `skill_directories` points at the **real** shipped bundle (no copying of live artifacts). `evals/` is already excluded from packaging (Plan 002), so eval files never ship.
- **Grader conventions bake in the two PoC gotchas — with the Gotcha-B fix corrected against verified waza 0.38 behavior (WZ-1).** Per case: (1) a cheap deterministic `text` regex pre-check (0 tokens); (2) the ported `rubric[]` as a `prompt` LLM-judge grader run as an **independent (fresh) judge session** (`continue_session: false`, waza's default = "waza starts a new Copilot session" for the judge). The PoC used `continue_session: true`, but verification shows that shares the agent's already-tainted context with the judge (the injection vector, DR-2), so it is **reversed**. Gotcha B (empty judge content when the agent's final turn is a tool call) is instead fixed with a task-level `follow_up_prompts` step that forces a final assistant **text** turn ("provide your final review as text"); waza runs graders only after all prompts complete, so the fresh judge then sees real content **without** inheriting the tainted session; (3) an **explicit `tool_constraint` override** in `eval.yaml` — Gotcha A: cr/dr declare VS-Code tool names (`read`/`search`/…) that copilot-sdk doesn't surface, so waza's auto-injected tool_constraint grader fails the whole task; the override suppresses it, replaced by a **real** `tool_constraint`/`tool_calls` (`required_tools`) once 1.0 maps the copilot-sdk tool names. Verified: `prompt` graders are strictly **binary** (judge calls `set_waza_grade_pass`/`set_waza_grade_fail`, score 1.0/0.0) — continuous 0–1 scores come only from `text`/`code`/`program` graders, so per-trial rubric acceptance is binary and the real threshold lives in `pass_rate` + deterministic pre-checks (see DR-3/DR-4 decisions). Use `trials_per_task ≥ 2` for agents (flaky), 1 for stable skills; judge by pass_rate not a single verdict.
- **Prompts excluded now; prompt→skill is a deferred workstream.** copilot CLI has no prompt executor, so the 3 `design-notes` prompt cases (`create`/`update`/`bootstrap-scaffold`) are excluded from the waza tier. Phase 4 converts each prompt to a skill (or confirms it's a pure alias over an existing skill), re-targets the cases, and adds the currently-missing `process-pr-comments` eval. Until then `design-notes` has no live LLM tier (Tier-1 Pester still runs).
- **waza's per-task workspace replaces the bespoke sandbox for Tier-2.** waza gives a disposable per-task workspace + fixture copy for free, so the old `New-EvalSandbox`/`Sync-Dogfood`/`Build-Registry`/push-disable dance is dropped for the LLM tier. Repo-relative agent context (`.github/agents/scripts/*.ps1`, design notes) is staged per case via fixtures/`--context-dir`/hooks, verified during each per-plugin dry-run.
- **cr/dr orchestrator-fidelity caveat is accepted (carried from Plan 005 RISK-11) — but fan-out is verified, not assumed.** cr/dr fan out to specialist subagents (`*-opus`/`-codex`/`-gemini`); headless copilot-sdk may run a single agent and not reproduce fan-out. Rubrics target **observable orchestrator output** (injection-guarded diff handling, structured findings), not multi-model consensus. The spike (1.0) **records whether fan-out actually occurs headless**; rubric claims are narrowed to verified behavior so cr/dr evals don't silently test a degenerate single-model path (DR-19).
- **A waza-behavior discovery spike (1.0) gates the migration — narrowed by verification and split into hard vs soft gates (DR-P3, WZ-5).** Verification against waza 0.38 already resolved several pass-1 unknowns from docs/CLI (so 1.0 shrinks to empirical confirmation, not open research): workspace isolation is documented (WZ-3), the injection path has a purpose-built harness (WZ-2), `SKILL.md` runs via `inject_skill_body`, `tool_calls`/`tool_constraint` expose real `required_tools`, and `waza migrate` handles `schemaVersion` bumps. 1.0 empirically confirms the rest **against the real cr bundle** and classifies each topic: **HARD gates** (a recorded fallback BLOCKS the affected cases rather than proceeding) = **workspace isolation / absolute-path containment** (a), **injection-harness efficacy** (b), **copilot-sdk tool-name mapping** (g); **SOFT gates** (record + proceed with the documented convention) = `skill_directories` resolution base (c), grader merge-vs-replace (d), `SKILL.md` execution shape (e), binary↔`schemaVersion` compat (f), model-slug placement (h), cr/dr fan-out (i). No off-ramp may relabel a failed HARD gate as "accepted risk"; it blocks the dependent step. 1.0 also **records the environment receipt** (resolved binary path, version, checksum, OS/arch, token source) since it runs the first live agent.
- **Live-tree write barrier: waza's per-task workspace is a verified isolation boundary, with an honest residual (DR-1, WZ-3).** Verification: waza runs each task in a **fresh temp workspace with the task's fixtures copied in — "originals never modified"** (`--keep-workspace` preserves it for inspection); the agent's cwd is that temp dir, **not** `plugins/`. `skill_directories` are read-only *discovery* paths waza uses to load the skill/agent body (injected via `inject_skill_body`), not the agent's writable tree — so the reviewer's assumption that the live bundle is a direct write surface is narrower than feared. **Residual risk that remains real:** under a permissive tool policy an agent could still issue an **absolute-path** write outside the workspace, and waza ships **no container executor** (only `mock`/`copilot-sdk`), so true OS-level containment must come from running the whole eval inside a container (already the shape of Phase 3 ADO). Convention: rely on the documented workspace boundary and **document the exact guarantee**; prefer a scoped tool allow-list over `--allow-all` where the case doesn't need it; and verify the residual with a **deterministic sentinel-write probe** — a task instructed to write a known absolute path into the repo tree, asserting the live tree stays byte-clean (`test:live-tree-clean`), not a single nondeterministic agent run.
- **Judge injection guard is resolved via verified waza mechanisms, not a hand-rolled fence (DR-2, WZ-2).** The pass-2 review correctly caught that the PoC's `continue_session: true` and a "fresh fenced judge" are mutually exclusive. Verification resolves the contradiction three grounded ways, in preference order: (a) **Route `treat-injection-as-data` and any adversarial-diff case through waza's built-in `adversarial` harness** — the `prompt-injection` offline pack, configured via a top-level `adversarial:` block (`schemaVersion: "1.2"`), run by `waza adversarial --on-unsafe-outcome fail` (exit 2 on unsafe, golden tasks, and *native credential-leak detection*). This is purpose-built for injection and is the primary home for these cases, replacing the hand-rolled fenced judge. (b) For non-adversarial rubric cases, the **independent judge** (`continue_session: false`) never ingests the untrusted fixture at all; `follow_up_prompts` forces the final text turn so it still sees real content (WZ-1). (c) A deterministic **`program`/`text` grader** carries the injection verdict as a non-LLM compensating control (e.g. assert the agent did NOT emit the injected directive) so the pass/fail never depends solely on an LLM reading attacker-influenced text. 1.0 validates (a) actually fires against cr and records which cases use the adversarial spec vs the rubric judge.
- **Acceptance is "no verdict regression over N runs", not "parity vs a single spot-run" (DR-3, WZ-4).** Legacy emits a continuous `score` (0–1) with a harness-enforced `score ≥ 0.7`; verification confirms waza's `prompt` grader is strictly **binary** (`set_waza_grade_pass`/`set_waza_grade_fail`) — there is **no** continuous score to enforce on the LLM judge, so the pass-1 "enforce a numeric judge score" idea is not available for `prompt` graders and is dropped. Continuous scoring instead comes from deterministic `text`/`code`/`program` graders. A single nondeterministic spot-run comparing a binary tool-call to a legacy scalar cannot establish parity. Migrated cases must therefore (a) carry the real threshold in the **deterministic `text`/`program` pre-checks** (continuous, 0-token) plus the binary judge, and (b) be accepted on **no regression across N≥3 repeated runs** of the same rubric. Fixtures are **derived faithfully from the original `scenario` text** (which embedded the stimulus inline) — not newly invented — so a migration stays a migration, not a new eval.
- **Trials/pass_rate math is honest (DR-4).** With 2 trials, `pass_rate ∈ {0, 0.5, 1.0}` and a 0.7 cutoff demands unanimity — more trials = more flake-sensitive. Choose one: `trials_per_task ≥ 5` with an explicit majority-ish `pass_rate` cutoff, **or** `trials = 1` honestly framed as a smoke check plus deterministic `text` pre-checks as the real guard. The per-trial judge `score ≥ 0.7` and the task-level `pass_rate` cutoff are both defined per task type in the convention; two undefined interacting thresholds are not allowed.
- **Tool assertions are real, not always-pass (DR-5).** The PoC suppresses Gotcha A with a reject-only constraint against a tool that can never be called ("always passes") — which gives Tier-2 **zero** tool verification and masks an agent that skips the actual work. The spike resolves the copilot-sdk tool-name mapping so migrated specs use a **real** `tool_constraint` (assert the review/read tools the agent should use) and step 2.4's `tool_calls` grader (build/test-before-commit) becomes implementable. The always-pass hack is a temporary PoC artifact, **not** the shipped convention.
- **Cost is modeled and a fast subset exists (DR-6).** 9 cases × trials × (agent + judge), with cr/dr fanning out, is unbounded as written. The runner records a token/wall-clock estimate, sets a per-run timeout + optional concurrency, and offers `-Plugin`/`-Case`/`-ChangedOnly` selectors and a `-Quick` (`trials=1`) mode for iterative use, so the tier is cheap enough to actually run.
- **No silent skip-to-green (DR-9).** `Resolve-EvalToken` and `Ensure-EvalTools` both end in `skip` to keep runs green, so a missing entitlement / declined install / checksum mismatch / empty discovery could all exit 0 having run **zero** evals. The runner enforces an **executed-count invariant**: if Tier-2 was requested but nothing executed, that is a distinct **non-green** outcome (clear message), separate from "all passed".
- **design-notes / process-pr-comments keep coverage — no orphaned cases (DR-8).** 2.6 must not leave the 3 design-notes cases runnable by no harness. Either the legacy `EvalLlm.psm1` path is **kept alive for design-notes only** until Phase 4 completes, or `EvalLlm.psm1` deletion is **blocked on Phase 4**. process-pr-comments' pre-existing zero LLM coverage is acknowledged as a known gap closed in 4.3, not silently normalized.
- **Model identity placement is decided, not incidental (DR-14).** The existing pattern keeps the judge/model slug in gitignored `.eval.config.json` (`.example` carries `<slug>`). If 1.0 finds waza requires the model in `eval.yaml`, the convention either (a) templates the slug from config at run time, or (b) documents committed slugs as an explicit exception with a **model-unavailable skip** path; either way REQ-10 and the design note state the config-vs-YAML precedence.
- **Checksum is a committed constant, not trust-on-first-use (DR-20, WZ-6).** The expected waza checksum is a committed value in `tools/eval-tools.psd1` applied to **both** online downloads and `offlinePath` vendored binaries — not fetched from the same release at run time. Provenance for the committed value is recorded once at pin time from the upstream release's published `checksums.txt` (the value + its source URL noted in a manifest comment), so a pin bump is a reviewable diff against a stated upstream artifact rather than a bare hash.
- **Adversarial/injection cases run under a durable-token exclusion (DR-P4, WZ-7).** A real Copilot token is injected into the `--allow-all` copilot-sdk child; over an adversarial fixture that is a credential-exfiltration surface. Mitigations, grounded in verified waza controls: (1) prefer the **short-lived `gh` OAuth token** (already the primary resolver source) over the durable Cred-Manager PAT for any adversarial run — auto-refreshed, short TTL limits blast radius; (2) run injection cases through `waza adversarial`, whose unsafe-outcome set **includes leaked credentials** (`--on-unsafe-outcome fail` → exit 2); (3) use waza's default-deny snapshot env (`--snapshot-env-allow` opt-in) and default-redacted OTEL payloads so the token isn't captured into artifacts; (4) do not surface a durable PAT to adversarial-case child env — segregate those cases to the short-lived token or an egress-restricted run. Encoded in the runner (REQ-22) and validated in 1.0(b).
- **`EvalLlm.psm1` full deletion is deferred to Phase 4 — no false "atomic delete" (DR-8, DR-P7).** Retiring the module in 2.6 while a design-notes shim still depends on it is a contradiction. Resolution: 2.6 **stops the 4 migrated plugins from using the LLM backend and removes their legacy JSON**, but the module stays intact to keep the 3 design-notes cases runnable; the module is **fully deleted in Phase 4** (4.4) once those cases are re-targeted to waza. REQ-8 verifies "migrated plugins no longer reference EvalLlm.psm1 and Tier-1 stays green," not module absence, until Phase 4.
- **Roles:** all steps `@ai-agent` except the corp-constraint/human-gate items in Phase 3 and the Finalization gate. **Execution-mode:** manual, phase scope.
