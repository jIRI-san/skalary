# Requirements

| ID | Requirement | Acceptance Criteria | Phases/Steps |
|----|-------------|---------------------|--------------|
| REQ-1 | Define closed draft-2020-12 schemas for frozen task plans and final `skalary/review-run@1` envelopes. Native PowerShell `Test-Json -SchemaFile` owns structural validation; semantic code owns cross-record and UTF-8 byte invariants. | A capability probe demonstrates the committed schema features on the minimum supported PowerShell; positive minimum/maximum fixtures pass; one-above, always-rejecting, unknown-version/property, duplicate, slot-mismatch, dangling, and aggregate-spoof fixtures fail at the named layer. `file:schemas/review/review-run.schema.json#exists` · `file:schemas/review/review-plan.schema.json#exists` · `test:ReviewReport.SchemaCapabilityAndSemantics` | 1.1, 1.2 |
| REQ-2 | Replace generated PowerShell findings and the in-process `-Finding <object[]>` API with a fixed installed `pwsh -File` CLI. It accepts only modes `Freeze` and `Publish`, `-RepoRoot`, UUID `-RunId`, and optional confined `-PlanDir`; it resolves its bundled schema and every artifact path itself. | Hostile quotes, here-strings, command substitutions, Markdown controls, traversal, alternate schemas/roots, and legacy object calls never become executable or caller-selected policy. Exact anchored approval rules cover only the two fixed command shapes. `test:ReviewReport.HostileInputIsData` · `test:ReviewReport.LegacyObjectApiRemoved` · `test:ReviewReport.ApprovalIsCommandLineBound` | 1.2, 2.1 |
| REQ-3 | Freeze the complete planned task set before any reviewer dispatch, then publish results only against that immutable plan. Every slot carries concern and declared dispatch model; final outcomes are `completed`, `failed`, `timed-out`, `omitted`, `cancelled`, or `pending`. | Freeze requires 1-128 unique task IDs and unique concern/model slots. Publish requires the exact frozen task set and immutable fields; every non-completed task has a bounded diagnostic; only completed tasks own findings; zero-finding completion is distinct; all-completed is clean and every other valid mix is degraded. `test:ReviewReport.FrozenPlanAndAttendanceMatrix` | 1.1, 1.2, 2.1 |
| REQ-4 | Preserve exact-key merge, strongest-severity selection, current full-declared-roster elevation, ordinal ordering, and recommendation behavior while deriving concern/model attribution from frozen tasks. Canonical semantic input, not raw JSON bytes, determines output. | A frozen golden corpus generated by the pre-change formatter proves byte-for-byte full-view parity apart from declared wording/layout changes; shuffled JSON properties, task/finding input order, culture, newline, and platform do not change canonical JSON or rendered bytes. `test:ReviewReport.GoldenMergeParityAndCanonicalization` | 1.1, 1.2 |
| REQ-5 | Publish canonical JSON as authority plus a summary of at most 32 KiB and full Markdown of at most 1 MiB. Structural maxima remain 128 tasks, 256 raw findings, and 128 merged groups, but exact UTF-8 byte-budget admission must prove both complete views fit. | Canonical JSON preserves every accepted task/finding. Summary names every merged severity/title and attendance totals; full view lists every task/finding with strongest body and bounded deltas. Reviewer-controlled fields are NFC/LF canonicalized, Markdown/HTML encoded, and fenced as untrusted data. Over-budget input fails without truncation. A representative 44-finding fixture reduces the measured chat rendering from about 66 KB to at most 32 KiB. `test:ReviewReport.OutputAdmissionCompletenessAndReduction` | 1.1, 1.2, 3.1 |
| REQ-6 | Use immutable generation files plus `review-run.manifest.json` as the sole publication commit point. `Freeze` writes the immutable plan before dispatch; `Publish` stages canonical JSON and both views, verifies byte bounds/digests, then atomically replaces the manifest last under an exclusive per-run lock. | Readers trust only a schema-valid manifest whose files/digests exist. Validation, bound, lock, injected publication, and unexpected failures leave the previous manifest authoritative; unreferenced staging/generation files are ignored and cleaned on retry. Module-scoped fault injection covers every publication edge. `test:ReviewReport.ManifestPublicationAndExitMatrix` | 1.2, 2.1 |
| REQ-7 | Both `/cr` and `/dr` follow the same run lifecycle: allocate UUID, write/freeze the plan before dispatch, update result input after each task returns, publish once, print the summary in chat, preserve the published path, and propagate degraded status after diagnostics are shown. | Installed instruction/eval fixtures prove ordering and command shape; executable clean/zero/degraded/invalid fixtures prove the installed binaries and artifacts. Tests state that model compliance beyond the installed instruction contract is residual, not mechanically proven. `test:ReviewReport.SharedCallerContract` · `test:ReviewReport.ConsumerInstallInvocation` | 2.1, 2.2 |
| REQ-8 | Keep schema, module/script, skills/guides, manifests, dogfood, settings approvals, design notes, marketplace, and registry synchronized with no new package or vendored validator. | Extend the existing bundle synchronizer with a closed schema-sidecar declaration and idempotent writer; assert root/plugin/dogfood hash parity, automatic single patch bumps, no package/lockfile changes, and structural eval discovery greater than zero. `test:ReviewReport.PayloadOwnershipAndDrift` · `test:ReviewReport.StructuralEvalDiscovery` · `test:ReviewReport.NoNewRuntimeDependency` | 2.1, 2.2, 3.1 |
| REQ-9 | `c21cdc` owns the v1 validation/persistence/rendering contract; `8a0644` owns future fleet task planning and emits this contract, while `ca8ba8` owns later similarity/corroboration policy. Both depend on `c21cdc`; neither may redefine v1. | Both plan markers and generated epic mirrors carry `c21cdc`; a real graph test resolves the cross-epic edges and proves both children blocked until completion. `ca8ba8` consumes v1 or introduces an explicit v2/migration; it does not mutate v1. `file:docs/implementation-plans/2026-08-08-ca8ba8-review-corroboration-truth/plan.md#contains:depends-on:[^>]*c21cdc` · `file:docs/implementation-plans/2026-08-08-8a0644-dispatch-plan-up-front/plan.md#contains:depends-on:[^>]*c21cdc` · `test:Epic.ReviewRunConsumersDependOnContract` | 1.1, 3.1 |
| REQ-10 | Give every run a canonical identity and lifecycle. Plan-associated runs publish under `<plan>/assets/reviews/<run-id>/`; other runs publish under gitignored `<repo>/.github/.skalary/review-runs/<run-id>/`; callers cannot provide another root. | `PlanDir` must resolve beneath the repo plan inventory and use its current/legacy layout; run IDs are lowercase UUIDs; changed input cannot reuse a published run ID; plan evidence is committed explicitly, generic runtime output is retained through the interaction and removed only by an explicit cleanup action. `test:ReviewReport.ArtifactLocationIdentityAndLifecycle` | 1.2, 2.1 |
| REQ-11 | Make encoding, canonicalization, exits, and diagnostics exact. Canonical JSON and Markdown are UTF-8 without BOM, LF, NFC, ordered by contract-defined ordinal keys, and hashed after canonicalization. | Exit `0` clean, `5` valid-degraded after publication, `2` invalid/schema/semantic, `3` byte/admission, and `4` lock/publication/unexpected; stdout contains only a bounded terminal JSON status with run/manifest paths and digest, stderr contains bounded encoded diagnostics, and error precedence is parse/schema -> semantic -> admission -> publication. `test:ReviewReport.EncodingExitAndDiagnosticContract` | 1.1, 1.2, 2.1 |
| REQ-12 | Bound implementation and verification cost and keep evidence discoverable. | Maximum legal envelope publishes within 5 seconds and 256 MiB private-byte growth on the supported container baseline; consumer installs reuse one fixture per plugin; renamed test IDs update the suite coverage baseline with reasons; named structural evals prove nonzero discovery; a new indexed review-reporting design note owns the durable contract and the ordinary suite remains inside platform ceilings. `file:docs/design-notes/architecture/review-reporting.design.md#exists` · `test:ReviewReport.MaximumEnvelopeBudget` · `test:ReviewReport.TestAndEvalDiscovery` | 1.1, 2.2, 3.1 |
