# Plan Workflow

> The `arch:` marker below is the plan-workflow **integration seam**; the full contract tier +
> ADR loop lives in [architecture-notes.design.md](architecture-notes.design.md) and the runner /
> receipt / gate enforcement in [architecture-tests.design.md](architecture-tests.design.md).

## Architecture

| Component | Responsibility | Notes |
|---|---|---|
| `plugins/create-implementation-plan/skills/cip/SKILL.md` | Orchestrates interview, drafting, DR rounds | Slim/orchestration-only; calls `New-Plan`/`Set-PlanStage`/`Add-WorkflowNote`/`Test-Plan` and embeds no validation or capture-schema prose; carries the anti-drift contract |
| `plugins/continue-implementation/skills/ci/SKILL.md` | Orchestrates step execution and crosschecks | Slim; reads state via `Get-PlanState`, captures via `Add-WorkflowNote` (layout-resolved capture log), builds receipts via `Build-EvidenceReceipt`; loads `assets/` on demand, never wholesale; retains resume/reset + `@human`/`[discovery]` judgment under the anti-drift contract |
| `scripts/skalary/Test-Plan.ps1` | Deterministic plan validator and file-evidence verifier | Supports `-Stage Draft|PhaseCrosscheck|PlanCrosscheck`; reusable evidence verification path |
| `scripts/skalary/PlanState.psm1` | Plan parsing + identity/resolution module | Holds `Get-PlanMetadata` (explicit `-RepoRoot`), `Get-PlanInventory`, `New-PlanId`, `Resolve-Plan`, the layout resolvers `Get-PlanLayout` / `Resolve-PlanAssetPath` / `Resolve-PlanSection`, the closed lifecycle stage set (`PlanStageOrder`, `Resolve-PlanStage`, `Test-PlanStageAtLeast`), and the shared validate/skip decision `Get-PlanValidationDecision`; pure parsing, no plan-text execution |
| `scripts/skalary/New-Plan.ps1` | Scaffolds a new plan folder from the cip template | Generates the id via `New-PlanId`, writes the `plan-id` anchor + `# <id>: <Title>` heading, stamps the `scaffolded` stage through `Set-PlanStage` (never writing the stage anchor itself), sanitizes + path-confines the slug, and scaffolds `assets/{intent,requirements,risks,decisions,references}.md` with explicit placeholders (never zero-length) |
| `scripts/skalary/Get-PlanState.ps1` | Plan progress + next-step state CLI (`npm run plan-state`) | Composes `Resolve-Plan`/`Get-PlanProgress`/`Get-NextStep`/`Get-PlanHeaderMarkers`; text or `-Json`; surfaces `@human`/`[discovery]`/blocked/uncommitted flags so `ci` collapses its read/find-next-step prose to one call. An epic reference returns `Kind = epic`: `Get-EpicRollup` output plus `NextChild` (`-Epic` forces epic resolution) |
| `scripts/skalary/New-Epic.ps1` | Scaffolds an epic folder + `epic.md` and stamps child plans | Writes `docs/implementation-plans/epics/<yyyy-mm-dd>-<6hex>-<slug>/epic.md`, stamps `<!-- epic: <id> -->` (and merges `<!-- depends-on: ... -->`) into child `plan.md` headers, and regenerates the `child-plans` mirror block for **every** epic a run touches; path-confined and idempotent |
| `plugins/create-implementation-plan/skills/cep/SKILL.md` | Orchestrates epic interview, decomposition, scaffolding | Thin; detail lives in `assets/decomposition-guide.md`. Scaffolds only after the operator accepts a cut, then hands each child to `/cip` for drafting |
| `scripts/skalary/Get-PlanIndex.ps1` | Cross-plan REQ / RISK / decision index (`Markdown` or `Json`) | Aggregates **active and archived** plans in both layouts via `Get-PlanInventory` + `Get-PlanMetadata`, so it sees exactly what the validator sees; deterministic by construction (ordinal ordering, repo-relative paths, no timestamps); optional `-Filter` regex narrows to a topic; a plan that fails to parse lands in `errors` instead of aborting the index. `/cip`'s `prior-art` gate reads this, never the plan corpus |
| `scripts/skalary/Set-PlanStage.ps1` | Idempotent `cip-stage` anchor writer | Single writer of the stage anchor and the gate on what may be written: `-Stage` is resolved through `Resolve-PlanStage`, so a value outside the closed set never reaches the file; `cip`/`dr` set the stage instead of hand-editing the header |
| `scripts/skalary/Add-WorkflowNote.ps1` | Typed mid-run capture writer | `-Kind` CrLog/Learnings/Capture → layout-resolved active logs plus `LearningOverflowRoot`; inventory/physical-link-confines `-PlanDir`, emits hash-bound typed provenance, and owns placeholders. One plan lock covers deterministic repair, overflow-first, and active replace. Every existing overflow envelope is schema/plan/count/filename/digest/byte validated before its IDs can drive dedup. Repair removes stale writer temps and duplicate/orphan active source ids, migrates old summaries while retaining `legacy-loss`, and makes replay idempotent. Candidate active and overflow stores are fully capacity-checked before the first write. Limits are 16 KiB/record, 64 records or 512 KiB/batch, 64 active batches/32 MiB, and 4 MiB/active log; plus-one is `capacity-blocked` exit 4 before mutation. |
| `scripts/skalary/Repair-Plans.ps1` | On-demand legacy loose-file migration | `-WhatIf`, idempotent no-op on clean, preserves `depends-on`/worktree markers and existing `plan-id`s; archived plans are a non-goal |
| `scripts/skalary/PlanEvidence.psm1` | Confined `file:` + `arch:` marker evaluator | Canonicalize-then-confine path checks, assertion vocabulary, regex/time budget enforcement; `Invoke-PlanArchEvidence` verifies an `arch:<ContractId>` marker by PURE-PARSING its receipt (no toolchain execution) |
| `scripts/skalary/ArchReceipt.psm1` | Shared arch-receipt substrate (single source of truth) | Canonical `Get-ArchTestSourcesHash` / check binding, the taxonomy x maturity `Get-ArchGateOutcome`, and pure-parse `Read-ArchReceipt`; imported by BOTH the arch-tests runner (producer) and `PlanEvidence.psm1` (verifier) so they never drift, and bundled into ci/cip/architecture-tests via the module closure |
| `scripts/skalary/Add-LedgerEntry.ps1` | Deterministic workflow-memory append and dedup writer | Sanitizes untrusted text, enforces category/src/severity enums, uses the shared `AtomicStore.psm1` workspace lock/replace + idempotent replay; accepts both legacy `\d{3}` and `[0-9a-f]{6}` hash plan ids and canonicalizes the reference via `Resolve-Plan` before writing |
| `scripts/skalary/Remove-LedgerEntry.ps1` | Deterministic workflow-memory prune/tombstone path | Full-line ordinal match, retention guards, `.archive/` move, no regex-driven destructive deletes |
| `scripts/skalary/Build-EvidenceReceipt.ps1` | Format-only per-REQ receipt aggregator | Pure formatter over verifier objects; emits the shared golden receipt line, never re-runs evidence. Optional `-PlanDir` returns the layout-resolved `.ReceiptPath` (`assets/evidence.md`, or root `evidence.md` for legacy plans) — it resolves the path but still never writes it |
| `scripts/skalary/Test-DependencyPlan006.ps1` | Hard phase-0 dependency start-gate | Resolves the guarded plan reference and every `depends-on` token through `Resolve-Plan`; pins compatibility-anchor tokens that slimming must preserve |
| `docs/review-ledger/**` | Durable workflow-memory store by category | Seven-category taxonomy + README contract; consulted on demand, never auto-loaded |
| `scripts/skalary/Validate-Plan.ps1` + `scripts/validate.ps1` | Repo-level and single-plan entry points | Keep validation pre-approvable and composable via npm scripts. `Validate-Plan` gates on the plan's lifecycle stage: below `drafted` it prints a `PLAN-VALIDATION: SKIPPED` signal and exits 0, at or above it prints `PLAN-VALIDATION: VALIDATING` and hands the plan to `Test-Plan` unchanged |
| `docs/implementation-plans/*/assets/evidence.md` | Receipt of typed evidence checks | Source of truth for archival-gate decisions; legacy plans keep it at the plan-folder root |

## Key Patterns

| Pattern | Contract |
|---|---|
| Plan identity (naming) | New plan folders use `<yyyy-mm-dd>-<6hex>-<slug>`; the 6-hex `hash` is the stable id, frozen in a `<!-- plan-id: <hash> -->` header anchor and addressable by any unique prefix ≥4 chars (git-short-SHA semantics). Legacy `NNN-<slug>` folders keep parsing in place — no renames. Legacy ids are exactly `\d{3}`; hash prefixes are ≥4 chars, so the domains never overlap by length. |
| Plan-id generation | `New-PlanId` emits 6 crypto-random hex chars (ids are intentionally non-reproducible, so no slug/timestamp hashing). It scans active **and** archived ids, regenerates on a full-id collision, and warns when the id is not uniquely addressable at the 4-char minimum prefix. |
| Plan resolution | `Resolve-Plan` normalizes any reference — hash prefix (≥4), legacy 3-digit number, slug, or date — to the canonical id (the `plan-id` anchor value, or the legacy number). A non-hex reference resolves by exact slug first, then a case-insensitive **substring** match — a partial slug resolves only when it uniquely matches one plan. A 6-digit all-numeric reference is a hash, not a legacy number (length disambiguates); ambiguous prefixes/substrings error git-style. |
| Typed evidence markers | Acceptance criteria use only `test:<TestId>`, `file:<path>#<assertion>`, `review:cr|dr`, and `arch:<ContractId>`. `Get-TypedEvidenceMarkers` (in `PlanState.psm1`) extracts the closed set; a marker-shaped token (`<prefix>:<value>`) whose prefix is NOT in the set is surfaced verbatim so the evaluator **fails loud** — a stale installed bundle that predates `arch:` blocks rather than silently dropping the marker and false-greening. |
| `file:` assertions | Closed vocabulary: `exists`, `contains:<regex>`, `count>=N`, `dircount>=N`. |
| Script-only validation | `cip`/`ci`/autopilot delegate validation to committed `.ps1` scripts; no in-chat or inline markdown validation logic. |
| Script distribution (bundling) | The state/validation scripts live once under `scripts/skalary/` (dev tooling + npm), but every script a shipped `ci`/`cip` skill invokes at runtime is **bundled into that plugin** (`plugins/<name>/skills/<skill>/scripts/`, installed to `.github/skills/<skill>/scripts/`) by `Sync-PluginScripts.ps1`, including the `PlanState.psm1`/`PlanEvidence.psm1` module closure. Those skills reference the installed `.github/...` path, never the repo-root `scripts/skalary/...` path, so they stay self-contained on install. (The autopilot agent still invokes these scripts via the repo-root `scripts/skalary/...` path because it always executes inside a checked-out repo; bundling autopilot is a tracked follow-up.) See plugin-registry.design.md → Skill Script Bundling. |
| Evidence receipt gating | Crosschecks rebuild the layout-resolved receipt; archival/finalization is blocked on unresolved `✗` or unrun required markers unless explicitly deferred in Decisions. |
| Ledger dedup-key contract | `Add-LedgerEntry.ps1` keeps two keys: idempotence key (`category + normalized-lesson + plan + src + severity + sorted-tags`, date excluded) and recurrence key (`category + normalized-lesson + sorted-tags`, plan/src/date excluded). |
| Ledger plan-id compatibility | The `$Plan` validator accepts `[0-9a-f]{4,6}` hash prefixes and `<yyyy-mm-dd>` dates alongside `\d{3}` (so `Resolve-LedgerPlanId` can fold any reference before writing), while the `ConvertTo-LedgerRecord` parse regex and the written entry string stay strictly `[0-9a-f]{6}` or `\d{3}`. Widening the parser rescues previously-unparseable well-formed `plan-<6hex>` entry lines so they survive append + canonical rewrite. The canonical rewrite reconstructs the file from the leading header block plus parseable `\d{3}`/`[0-9a-f]{6}` entry lines only — interleaved free-form or malformed lines placed after the first record are not preserved. The reference is folded to one canonical id via `Resolve-Plan` before any key is built, so dedup/recurrence keys never fork across schemes; only `[0-9a-f]{6}` or `\d{3}` is ever written. |
| Shared receipt grammar | `Build-EvidenceReceipt.ps1` is the single emitter of the golden per-REQ line `<glyph> REQ-N — <marker> — <result> — <commit>` (em-dash `U+2014` with surrounding spaces; `✓ U+2713` pass, `✗ U+2717` fail/unrun; result `passed`/`failed`/`unrun`, optional `: <note>`). A REQ passes only when **all** its markers pass; failed and unrun markers are preserved verbatim. The receipt is format-only — it never re-runs evidence. |
| Workflow-memory capture | Mid-run writes are script-mediated via `Add-WorkflowNote.ps1` (layout-resolved `cr-log` / `learnings` / `capture` plus `learning-overflow`) with explicit phase placeholders. Entries carry closed concern/review types, plan-validated sorted REQ ids, and kind-domain-separated source-record ids. The 10-entry active cap is **Learnings-only**; overflow is persisted first as an append-only content-addressed batch, while old summary lines are retained and reported as `legacy-loss`. `CrLog` and `Capture` are uncapped. |
| Shared writer durability | `AtomicStore.psm1` is root-canonical and bundled by import closure into PFB, CI, CIP, SI, and autopilot. Feedback, workflow-note, ledger, and SI state writers share its repo-scoped lock, generation digest, same-directory random temp, validation hook, atomic replace, three-conflict retry, and closed `complete` / `lock-timeout` / `cas-conflict` / `cas-exhausted` / `capacity-blocked` / `invalid` status vocabulary. |
| Ledger bootstrap | `docs/review-ledger/` sits outside `.github/`, so installation cannot write it. `Add-LedgerEntry.ps1` creates the category file (and `Remove-LedgerEntry.ps1` the `.archive/` folder) on first use rather than throwing — otherwise the first harvest in every consumer repo fails, and prune stays permanently and silently disabled. `-Category` is a closed enum and the path is confine-resolved, so the write target stays bounded. Both are declared as `scaffolds[]` entries on the owning plugin. |
| Workflow-memory harvest | `LedgerStore.psm1` is the single bounded scalar/batch engine behind `Add-LedgerEntry.ps1` and `Invoke-PhaseHarvest.ps1`. The phase harvester validates typed source-record provenance, binds repo/plan/phase/kind/review/path/exact record bytes into source ids, routes through the closed concern map, batch-writes each category once, and persists an immutable layout-resolved receipt for replay. Prune remains escalation-only and script-mediated via `Remove-LedgerEntry.ps1`. When the `architecture-notes` plugin is installed, `/ci` finalization **also** harvests the plan's decision records (`assets/decisions/*.md`, or legacy `decisions/*.md`) into proposed ADRs via `Import-ArchAdr.ps1` — quarantined `reviewed:false` under `docs/architecture-notes/.staging/adr/` for human promotion into the arch tier (see [architecture-notes.design.md](architecture-notes.design.md) → ADR feedback loop). |
| Post-plan feedback (`/pfb`) | Typed evidence proves the requirements; only the operator can say the work met the point, so `/ci` **offers** `/pfb` at the archival gate and never gates on it — a declined or unanswered run blocks nothing, and a recorded verdict never substitutes for a `✗` marker. Verdicts land in `docs/feedback/queue.md` through `Update-FeedbackQueue.ps1` (script-owned; `## Pending` holds questions a headless run could not ask, `## Recorded` holds operator answers, both sanitized and round-trip-validated against the entry grammar). Autopilot has no operator, so it queues the question instead of prompting and the next interactive session consumes the marker by id. |
| Epic layer | An epic is an **index**, never a container: `epic.md` lives under `docs/implementation-plans/epics/<date>-<6hex>-<slug>/` while child plans stay ordinary sibling plan folders, so `Resolve-Plan`, the validator, and every existing consumer keep resolving them unchanged. Membership is the `<!-- epic: <id> -->` header marker in the child (read through the same header-scoped view as every other marker, so a documented example in a plan body enrolls nothing); ordering reuses `<!-- depends-on: ... -->`. `epic.md`'s child table is a generated mirror between `<!-- child-plans:start/end -->`. Epic ids and plan ids share one id space — `New-Plan` and `New-Epic` collision-check both directions — so `/ci <id>` is unambiguous. |
| Epic rollup and child selection | `Get-EpicRollup` aggregates child progress and picks `NextChild`: the first child in `(Date, Id)` order that is neither complete nor blocked. A child is complete when every step is `[x]` **or** its plan is archived (archival is terminal, so dependents must not stay blocked behind it). A `depends-on` may point outside the epic — completeness is judged from the dependency plan's own state, never from membership — and resolution is fail-closed: a token resolving to no plan or several blocks the child and is reported. `/ci` takes `NextChild` rather than choosing a child itself. |
| Plan folder layout | A plan folder root holds only `plan.md`. Everything else lives under `assets/`, including `assets/logs/{capture,cr-log,learnings,learning-overflow/**}` and `assets/harvest-receipts/**`. Legacy plans permanently resolve those roots to `learning-overflow/**` and `harvest-receipts/**` beside their flat logs. |
| Layout resolution | `Get-PlanLayout` keys on `assets/requirements.md`; `Resolve-PlanAssetPath` maps file and root kinds, including `LearningOverflowRoot` and `HarvestReceiptRoot`, to permanent assets/legacy locations. Writers pass repo root + inventory; the resolver walks existing path components through link targets before returning, so a forged directory or symlink cannot escape or target a non-plan folder. |
| Section resolution | `Resolve-PlanSection` runs **inside `Get-PlanMetadata`** (not at the `Test-Plan` boundary) and resolves per section, so `Test-Plan`, `Get-PlanState`, and `Get-NextStep` all see identical data. State table: asset absent → fall back to the in-`plan.md` table; asset present, non-empty, well-formed → asset wins; asset present but empty or malformed → **fail loud** (never silently zero records); both present → asset wins and **divergence errors**. Divergence compares the normalized parsed record set (cells whitespace-collapsed, rows order-insensitive), not raw text, so cosmetic drift is not an error. `Remove-FencedCodeBlocks` applies to asset files exactly as it does to `plan.md`. |
| Phase budget cap | `Test-Plan.ps1` reads the `<!-- phase-budget-points: N -->` header marker and warns per phase against it; absent or non-numeric falls back to 6. The cap is advisory (a warning, never an error) — as are both plan-size thresholds. |
| Operator intent | `/cip` captures intent (`Goal` / `Desired outcome` / `Success signals` / `Non-goals` / `Definition of done`) into the layout-resolved intent asset before drafting; the `intent` gate in `interview-guide.md` blocks drafting while the asset is missing or any section is still `TBD`. `/ci` reads it before every step and re-anchors at phase and plan crosscheck. The five sections are one shape shared by `intent-template.md`, the `New-Plan.ps1` scaffold, and the gate — bound by test so a rename cannot silently disarm the gate. Gate enforcement is prose-level (interview conduct), not a validator check. |
| `prior-art` gate | Before drafting, `/cip` reconciles against earlier plans through `Get-PlanIndex.ps1` — the generated cross-plan index, never the plan corpus, which does not scale with the archive and hides archived decisions. Every record the index returns for the topic must be recorded as reuse / extend / supersede (naming the prior plan id + record id and the reason) or resolved as a conflict with the operator. Like `intent`, enforcement is prose-level interview conduct, not a validator check. |
| `human-step-detail` gate | An `@human` step must carry a `<details>` block containing **Steps**, **Verify**, and **Rollback** (bold headings or bold-prefixed list items). `Test-Plan.ps1` errors on any gap in an opted-in plan and `Get-PlanState` prints the same block under `Handoff:`, so the operator round-trip is single-pass. Archived plans are **warn-only** — the gate governs plans being drafted and executed, not historical records, and `scripts/validate.ps1` validates archived plans too. |
| Step detail capture | `Get-PlanMetadata` attaches every `<details>` block under a step to `step.Detail`. Text is taken from the **raw** lines, not the fence-stripped copy, so fenced operator commands survive; nesting is depth-counted on the stripped lines so a fenced example cannot close the real block; all blocks under a step are collected (plans also carry Result/evidence blocks); an unindented step line always terminates capture so an unterminated block cannot swallow the rest of the plan. |
| cip package-awareness | For autonomous container/sandbox plans, `cip` interviews for expected new packages (`interview-guide.md`), records them in the optional `<!-- expected-packages: dotnet:<list>; npm:<list> -->` header marker (`plan-template.md`, `none` when none), and drafts package-adding steps batched into a single early phase (`drafting-guide.md`) so the offline rebundle round-trip fires at most once. The marker is advisory — no validator gate. |

## Design Decisions

- An epic indexes sibling plan folders instead of nesting them. Nesting would have forced every consumer — inventory, resolver, validator, ledger, archival — to learn a second folder shape, and would have made "independently executable child plan" structurally false. Indexing keeps the child a plain plan and confines epic knowledge to `New-Epic` + the rollup.
- The epic's child table is derived state, rebuilt from the markers on disk on every run, including for the epic a `-Force` re-parent moved a child *away* from. A mirror that is only refreshed for the invocation target is a second source of truth that goes stale exactly when membership changes.
- A plan reference keeps winning over an epic reference in `Get-PlanState`. Both resolvers accept fuzzy date and slug forms, so preferring epics would break references that already resolved to a plan; hex ids are unique across both spaces, so `/ci <epic-id>` still lands in epic mode and `-Epic` forces the fuzzy forms.
- Plan parsing lives in `PlanState.psm1` so `Test-Plan.ps1`, `New-Plan.ps1`, and the state CLI share one parser. `Get-PlanMetadata` takes an explicit `-RepoRoot` parameter (it previously closed over a script-scoped variable, which a module function cannot inherit under `Set-StrictMode`); all call sites pass it and parity is proven under a non-default `-RepoRoot`. `Get-TypedEvidenceMarkers` also lives here (the shared parser) so the closed marker vocabulary and its fail-loud-on-unknown-prefix behavior are single-sourced.
- The plan layout resolver lives in `Get-PlanMetadata`, not at the `Test-Plan` call boundary. `Get-PlanMetadata` builds `.Requirements` / `.Risks` / `.Decisions` for every consumer, so resolving only at the validator would leave `Get-PlanState` and `Get-NextStep` with zero requirements the moment a plan migrated. Resolution is **per section**, not per plan: an `assets/` folder holding no recognized files falls back section-by-section rather than switching the whole plan into a broken mode.
- Empty and malformed assets fail loud instead of falling back. A silent fallback would turn a truncated `assets/requirements.md` into "this plan has no requirements", which greens every REQ gate. `New-Plan` therefore scaffolds placeholders with real content so "present-but-empty" stays distinguishable from "authored".
- Migrating a plan to the assets layout must be a single atomic edit — write the asset files and remove the in-`plan.md` tables together, then re-validate before committing. `/ci` picks the first incomplete step in document order and re-parses the plan between steps, so a committed half-state would be mis-parsed by the very next `Get-PlanMetadata` call. `test:migration-is-atomic` asserts no plan folder is left with neither a legacy table nor its asset.
- The `arch:<ContractId>` marker verifies an **integrity/freshness receipt** by pure parse — it never executes a toolchain or plan/contract text. `Invoke-PlanArchEvidence` (in `PlanEvidence.psm1`) locates the receipt, schema-validates it (malformed/mismatched → fail loud), rejects a STALE receipt by **recomputing the canonical sources hash** (from the committed config binding + contract/target sources) and comparing to the recorded `sourcesHash` — freshness binds to the tree/content hash, not raw `HEAD` equality, so committing the receipt does not self-invalidate it — then maps the recorded verdict through the shared taxonomy x maturity gate (`locked`: only a real `pass` greens; `fail`/`error`/`skip-absent-toolchain` block; `draft`/`provisional` warn; `semantic-eval` advisory-always). The hashing/gate/read logic lives in `ArchReceipt.psm1`, imported by both the runner (producer) and the marker (verifier) so a false-green cannot arise from the two sides drifting.
- The gate-steering fields are taken from the **trusted config/contract, not the receipt's own copies**: the verifier derives the adapter from the config check and the effective maturity from the contract (governing) then config (`Resolve-ArchEffectiveMaturity`, shared with the runner's derivation), cross-checks the receipt's `adapter`/`maturity` against them (mismatch → fail loud), and gates on the derived values — closing the false-greens where a hand-edited `receipt.adapter=semantic-eval` or `receipt.maturity=draft` would downgrade a locked `fail` to an advisory warn. `verdict`/`ran` are the run **output** and exist only in the receipt; per the trust anchor (git history + human commit, **not** crypto) they are reviewer-enforced — the marker rejects stale/malformed, not a receipt forged by a party with commit access (a human reviewing the committed receipt + contract in the same PR is the tamper-evidence). The shared hasher confines source paths to the repo root, skips symlinks, and caps per-file bytes so an escaping/oversized config target cannot read arbitrary host content into the digest.
- Plan ids are random, not content-derived: a hash of slug/timestamp adds no recoverable meaning when ids are non-reproducible by design, so `New-PlanId` uses crypto-random hex and resolves collisions by scanning the active + archived inventory. `Repair-Plans` (and any migration) must never mutate an existing `plan-id` anchor.
- A plan's id is written into the ledger and `depends-on:` in exactly **one** canonical form; callers resolve any reference to that canonical form via `Resolve-Plan` before writing, so dedup/recurrence keys never fork across the legacy/hash schemes. The `Test-DependencyPlan006` start-gate resolves both the guarded reference and each declared dependency the same way, so a legacy `006` and a hash-style dependency trigger identical preflight behavior.
- Ledger hash-id compatibility preserves **well-formed** entry lines: widening the parser (validator + `ConvertTo-LedgerRecord` regex + entry string) was co-edited so previously-unparseable `[0-9a-f]{6}` entry lines become records and survive the canonical rewrite instead of being silently dropped. The rewrite reconstructs from the leading header + parseable records, so it does not guarantee retention of interleaved comments or malformed/short-hex lines placed after the first record; a mixed-format round-trip regression test guards the entry-line case.
- Evidence receipts have one golden grammar emitted only by `Build-EvidenceReceipt.ps1`; orchestrators and autopilot consume that shared formatter rather than hand-writing receipt lines, so the receipt shape stays identical across `ci`/`cip`/autopilot.
- The workflow scripts have a single source of truth (`scripts/skalary/`) but are duplicated into each consuming plugin rather than shared through a runtime module or a common plugin. Plugins install and are versioned independently, so a shared runtime location cannot guarantee a compatible script is present; managed duplication (generated by `Sync-PluginScripts.ps1`, drift-gated to byte-identical) is the accepted cost of that independence. Consequently, **a change to any shared script bumps the `version` of every plugin that bundles it** — the edit is a payload change to each dependent plugin.
- `Test-Plan.ps1` is the single validation authority so approval/allowlist models stay stable across host/container/autopilot execution.
- The `human-step-detail` gate is exempted for archived plans rather than blanket-warn or retro-fitted. `scripts/validate.ps1` validates every plan file including `docs/implementation-plans/archived/`, and existing archived plans predate the gate; making the gate advisory everywhere would leave the requirement unenforced, while editing archived plans would rewrite history to satisfy a rule that did not exist. `IsArchived` is derived from the plan's own resolved path (an `archived` folder directly under `implementation-plans`), not from `-RepoRoot`, which may be relative and would resolve against the wrong base.
- Step detail is captured from the **raw** plan lines rather than the fence-stripped copy used for structural parsing. `@human` handoffs routinely carry fenced operator commands, and capturing the stripped copy would silently hand the operator prose with the commands blanked out — the exact failure the gate exists to prevent.
- Stage-aware validation avoids self-blocking plans during drafting while still enforcing strict verification at crosscheck/finalization.
- Plan lifecycle stages are a **closed, ordered set** defined once in `PlanState.psm1` (`scaffolded` < `drafted` < `dr-round-<n>` < `done`). Any reader that treats "not `drafted`" as "skip validation" turns a typo into a pass that exits 0 while checking nothing, so an unrecognised value throws instead of resolving to a skip, and `Set-PlanStage` rejects it at write time. Two deliberate asymmetries: a **missing** anchor resolves to `drafted` (older plans keep being validated exactly as before), and a caller-supplied floor is ranked against the family list so every value `Get-PlanStageOrder` publishes is a usable floor — a bad floor blames the caller, a bad anchor blames the plan.
- Evidence is machine-checkable only; non-deterministic markers (`cmd:`/`manual:`) are excluded to preserve autopilot safety and repeatability.
- A skipped validation announces itself, and there is only one floor. `npm test` validates plans twice — `Validate-Plan.ps1` for the working plan, `scripts/validate.ps1` for the whole tree — so both call `Get-PlanValidationDecision` and print the `PLAN-VALIDATION: SKIPPED …` / `PLAN-VALIDATION: VALIDATING …` signal it returns. A floor honoured by only one leg would be cosmetic: the below-floor plan is skipped by one and hard-failed by the other, changing nothing but which leg reports it. Exiting 0 with no signal is equally useless, because a silent skip is indistinguishable from a pass to anything reading the exit code. Default plan resolution resolves the stage of **every** candidate, so a plan carrying a bad marker fails on the spot instead of waiting until it happens to be selected.
- Workflow-memory mutation is script-only (`Add`/`Remove`) and invoked through bound argument arrays; orchestrators do not hand-edit ledger files.

## Constraints

- Plan text is untrusted input. Validation scripts must use pure parsing/bound parameters (no dynamic command execution from plan content). New-plan slug input is sanitized to `[a-z0-9-]` and canonicalize-then-confined under `docs/implementation-plans`.
- Plan identity is dual-format: legacy `NNN-<slug>` folders keep parsing and stay in place; only new plans use `<date>-<hash>-<slug>`. The `plan-id` anchor is the canonical id and is never rewritten by migration.
- A legacy `NNN-<slug>` folder must not carry a divergent hex `plan-id` anchor: `Get-PlanInventory` sets the canonical id to the anchor value when present, so a mismatched anchor makes the plan unaddressable by its 3-digit number and can fork ledger/`depends-on` keys.
- Header anchors (`plan-id`, `cip-stage`) are read/written file-wide today (`Get-PlanInventory`, `Set-PlanStage`), not header-scoped like `Get-PlanHeaderMarkers`. Keep these anchors in the pre-`##` header and never place an example `<!-- plan-id: ... -->` / `<!-- cip-stage: ... -->` in the body — a body occurrence can hijack canonical identity or block the real stage write.
- `Get-PlanState`'s uncommitted-changes probe is best-effort/fail-open: a `git status` failure reports a clean tree, so the explicit commit gate (not this flag) remains the authority on dirty-tree state.
- Legacy plans without `<!-- evidence: required -->` run in warn-only mode for strict integrity classes; opted-in plans enforce blocking behavior.
- Log and receipt paths are layout-dependent. Any new writer or reader of a plan-folder file must resolve through `Resolve-PlanAssetPath` (or a script that does); hard-coding either the `assets/` or the legacy root path reintroduces the split-brain REQ-20 exists to prevent.
- Any workflow change that alters marker grammar, stage semantics, completion gates, or the plan naming/id scheme must update this note and the relevant `cip`/`ci` assets in the same change.
- Any edit to a `scripts/skalary/` script that is bundled into a plugin must re-run `Sync-PluginScripts.ps1` (which re-copies the bundle and **patch-bumps the `version` of every plugin that bundles that script**), then rebuild `registry.json`, in the same change; the `Sync-PluginScripts.ps1 -WhatIf` bundle drift gate in `scripts/validate.ps1` fails CI otherwise.
