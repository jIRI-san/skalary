# Plan Workflow

Architecture contracts remain human-owned context in the architecture-notes tier. Plan evidence is
limited to deterministic test, file, and review markers; retired marker prefixes fail loud.

## Architecture

| Component | Responsibility | Notes |
|---|---|---|
| `plugins/create-implementation-plan/skills/cip/SKILL.md` | Orchestrates interview, drafting, DR rounds | Slim/orchestration-only; calls `New-Plan`/`Set-PlanStage`/`Add-WorkflowNote`/`Test-Plan` and embeds no validation or capture-schema prose; carries the anti-drift contract |
| `plugins/continue-implementation/skills/ci/SKILL.md` | Orchestrates phase admission, step execution, and crosschecks | Slim; performs a read-only phase admission over existing `PlanState` APIs before any worktree/checklist/log mutation, captures via `Add-WorkflowNote` (layout-resolved capture log), builds receipts via `Build-EvidenceReceipt`; loads `assets/` on demand, never wholesale; retains resume/reset + `@human`/`[discovery]` judgment under the anti-drift contract |
| `scripts/skalary/Test-Plan.ps1` | Deterministic plan validator and file-evidence verifier | Supports `-Stage Draft|PhaseCrosscheck|PlanCrosscheck`; reusable evidence verification path |
| `scripts/skalary/PlanState.psm1` | Plan parsing + identity/resolution module | Holds metadata/inventory/identity parsing, layout resolvers, physical plan-confinement and stable read-handle authority, lifecycle and planning-context state, plus the pure `Get-PhaseAdmission` and `Get-PhaseCheckpointOptions` policy functions; no plan-text execution |
| `scripts/skalary/New-Plan.ps1` | Scaffolds a new plan folder from the cip template | Generates and collision-checks the id; writes the plan heading/markers; stamps `scaffolded` through `Set-PlanStage`; sanitizes/path-confines the slug; and scaffolds non-empty `assets/{intent,domain,design,requirements,risks,decisions,references}.md`. New scaffolds enroll in planning confirmation as `pending`. |
| `scripts/skalary/Get-PlanState.ps1` | Plan progress + next-step state CLI (`npm run plan-state`) | Composes resolver/progress/next-step/header state; text or `-Json`; surfaces planning context (`legacy|pending|confirmed|stale|missing|invalid`) alongside `@human`/`[discovery]`/blocked/uncommitted flags. An epic reference returns rollup plus `NextChild`. |
| `scripts/skalary/Get-PhaseExecutionState.ps1` | Runtime-neutral phase-close probe | Reuses canonical admission, checklist, and immutable harvest-receipt validation; returns `execution-required`, `close-pending`, or `closed`, while malformed state fails. |
| `scripts/skalary/New-Epic.ps1` | Scaffolds an epic folder + `epic.md` and maintains child membership | Writes `docs/implementation-plans/epics/<yyyy-mm-dd>-<6hex>-<slug>/epic.md`, stamps `<!-- epic: <id> -->` for later attachment/re-parenting, reconciles an already-prefixed plan folder to the new epic prefix with platform-aware path equality after non-dereferencing collision/confinement preflight, validates the generated child-table blocks for the target and every losing epic before child mutation, rolls back the child header if the folder move fails, merges `<!-- depends-on: ... -->` into child headers, and regenerates the `child-plans` mirror block for **every** epic a run touches; idempotent. Legacy and rollout-era unprefixed folders keep their paths. Initial `/cep` membership is written by `New-Plan -EpicId` so the child starts under its final name. |
| `plugins/create-implementation-plan/skills/cep/SKILL.md` | Orchestrates epic interview, decomposition, context-preserving scaffolding | Thin; detail lives in `assets/decomposition-guide.md`. Scaffolds only after the operator accepts a cut; the `child-context` gate then requires preliminary intent, settled/rejected decisions, unresolved uncertainty, and dated epic-discussion provenance in every child before handoff to `/cip` |
| `scripts/skalary/Get-PlanIndex.ps1` | Cross-plan REQ / RISK / decision index (`Markdown` or `Json`) | Aggregates **active and archived** plans in both layouts via `Get-PlanInventory` + `Get-PlanMetadata`, so it sees exactly what the validator sees; deterministic by construction (ordinal ordering, repo-relative paths, no timestamps); optional `-Filter` regex narrows to a topic; a plan that fails to parse lands in `errors` instead of aborting the index. `/cip`'s `prior-art` gate reads this, never the plan corpus |
| `scripts/skalary/Get-PlanArtifactContext.ps1` | Internal bounded cross-plan artifact resolver | Accepts exact canonical IDs selected by index/epic/dependency/operator discovery, fails once when `RepoRoot` lacks the canonical plan corpus, inventories only requested canonical folder IDs, maps either one shared relationship or an aligned relationship per selected plan, and resolves the closed Intent/Design/Decisions/Reviews/Evidence/Learnings set through `PlanState.psm1`. Consumers never invoke it directly; only the sibling adapter requests `-Format Json`. `PlanState` first binds a physical repository/corpus authority, rejects linked corpus ancestors, and then creates one physically nested confinement context per selected plan; it owns path admission, stable handles, OS identity, single-link checks, and the second-handle comparison. Public opens expose no synchronization delegate; race tests enter the module's internal core seam. Each candidate walk starts at the cached physical plan root. Runtime ABI admission is fail-closed: Windows and Linux layouts are admitted as documented, while macOS is explicitly refused because variadic `F_GETPATH` P/Invoke is not ABI-safe. Every result carries plan ID, kind, repo-relative path, relationship, layout/archive state, returned-content UTF-8 byte count (or null), and the historical-untrusted authority fence. Decisions validation still uses `Resolve-PlanSection`, while returned asset bytes and legacy section bytes retain fenced rationale; companion plan/receipt bytes count against resource limits but never inflate the returned-content byte count. Reviews require a finalized report/receipt pair validated from the already-confined bytes by the canonical `ReviewResultReceipt.psm1`; `PlanEvidence.psm1` retains an exact compatibility export for plan-finalization callers, so independently versioned plugin bundles cannot remove the resolver's validation API. Missing, unsupported, malformed, linked/non-regular, invalid UTF-8, empty, whitespace-only, and oversized candidates return single-line bounded diagnostics with no content. Selection and expansion overflow preserve at least one diagnostic for every requested plan/artifact combination without overwriting already-specific missing/refused reasons. Reads default to 128 KiB per artifact, 512 KiB aggregate, and at most 32 open candidates/handles; bounded diagnostic output may exceed that work cap, up to the closed request-shape maximum. |
| `scripts/skalary/Get-PlanArtifactConsumerContext.ps1` | Sole consumer-facing executable protocol | Runs the sibling resolver in an isolated process with a 30-second default/120-second maximum wait, terminates the process tree on timeout, requires exit zero plus non-whitespace top-level array JSON and the closed result shape, and emits index/plan/path/key-aware bounded diagnostics. Successful stderr is a warning; failed and successful stderr diagnostics are control-sanitized, secret-redacted, and truncated. Before prompt framing it applies the shared `SecretGuard.psm1` high-confidence detector: a hit converts only that artifact to a redacted refusal naming type and path. Accepted metadata and provenance stay outside the model frame; artifact content appears exactly once, inside complete accepted objects in the standard `UNTRUSTED_INPUT` fence. CIP, CEP, plan-associated CR, and in-repo DR invoke this adapter directly, but terminal approval is intentionally required because the installed sibling closure is not digest-bound. Parse/shape/process failure is fatal. Shared protocol prose lives in byte-identical `assets/plan-artifact-consumer-protocol.md` payloads; each guide keeps only consumer-specific selection/provenance behavior. |
| `scripts/skalary/Set-PlanStage.ps1` | Lifecycle and planning-confirmation marker writer | Single writer of `cip-stage` and `planning-confirmed`. `-ConfirmPlanningContext` validates authored intent/design and writes `sha256:<digest>`; enrolled plans cannot advance to `drafted` or later while pending/stale. Marker-less plans remain legacy-compatible. |
| `scripts/skalary/Add-WorkflowNote.ps1` | Typed mid-run capture writer | `-Kind` CrLog/Learnings/Capture → layout-resolved active logs plus `LearningOverflowRoot`; inventory/physical-link-confines `-PlanDir`, emits hash-bound typed provenance, and owns placeholders. One plan lock covers deterministic repair, overflow-first, and active replace. Every existing overflow envelope is schema/plan/count/filename/digest/byte validated before its IDs can drive dedup. Repair removes stale writer temps and duplicate/orphan active source ids, migrates old summaries with content-and-file-version observation provenance while retaining `legacy-loss`, and makes replay idempotent across every temp/commit crash boundary without discarding a later identical summary after an ABA rewrite. Candidate active and overflow stores are fully capacity-checked before the first write. Limits are 16 KiB/record, 64 records or 512 KiB/batch, 64 active batches/32 MiB, and 4 MiB/active log; plus-one is `capacity-blocked` exit 4 before mutation, while `lock-timeout` is surfaced and exits 5 rather than silently dropping capture. |
| `scripts/skalary/Invoke-PhaseHarvest.ps1` | Immutable phase-capture harvest | Reads exactly one executable phase section from each workflow log, permits legacy Phase 0 planning records only in Capture, and permits generated empty Phase 0 placeholders in the other logs. Non-Capture Phase 0 records fail before harvest so planning context cannot enter executable review or learning authority. |
| `scripts/skalary/ReviewCycleGate.ps1` | Durable `/ci` + autopilot CR-loop cap | Counts machine-shaped cycle/decision/remediation notes in the layout-resolved CR log. Current execution uses `phase-*` and `plan-finalization`; legacy `step-*` records remain readable. Cycles 1–3 are automatic; after that an operator Continue grants exactly one additional cycle, while Wrap ends the loop with findings retained. `InvalidateContinue` appends a SHA-256-targeted remediation for only the unique latest Continue when no review followed. `InvalidateReopen` is the narrower incident-repair path: it requires the exact 64-hex typed workflow source-record id, explicit repair authorization/reason/repo root, unique inventoried plan confinement, source-record digest agreement with plan + supplied phase, a unique latest Reopen immediately after Wrap, and no later cycle/event. It preserves both records and derives the prior Wrap again; stale, duplicate, ambiguous, legacy-clean, post-review, unconfined, and tampered targets fail before mutation. Headless autopilot exits 42 rather than granting itself continuation or Reopen authority. |
| `scripts/skalary/Repair-Plans.ps1` | On-demand legacy loose-file migration | `-WhatIf`, idempotent no-op on clean, preserves `depends-on`/worktree markers and existing `plan-id`s; archived plans are a non-goal |
| `scripts/skalary/Migrate-PlanFolderPrefixes.ps1` | Optional rollout-era hash-plan folder migration | Defaults to a non-moving inventory pass over active and archived unprefixed hash plans and atomically writes a deterministic, versioned old/new mapping only after plan-id, epic-membership, collision, and physical-confinement preflight succeeds; `-Apply` consumes only that mapping, revalidates the complete corpus under the repository atomic-store lock, moves sequentially, records each completion atomically, and resumes the move-before-record interruption window idempotently |
| `scripts/skalary/PlanEvidence.psm1` | Shared evidence normalizer, policy/parser host, and confined `file:` evaluator | Closed outcome vocabulary, exact plan-local waiver validation, bounded receipt parsing, layout-confined receipt/policy paths, canonicalize-then-confine file checks, and regex/time budget enforcement |
| `scripts/skalary/Add-LedgerEntry.ps1` | Deterministic workflow-memory append and dedup writer | Thin scalar compatibility entry point over `LedgerStore.psm1`; sanitizes untrusted text, enforces category/src/severity enums, uses the shared atomic lock/replace + idempotent replay, canonicalizes legacy/hash plan references before writing, and indexes idempotence/recurrence keys plus plan resolutions once per batch so the 10,000-record/4,096-candidate boundary stays subquadratic |
| `scripts/skalary/Remove-LedgerEntry.ps1` | Deterministic workflow-memory prune/tombstone path | Full-line ordinal match, retention guards, `.archive/` move, no regex-driven destructive deletes |
| `scripts/skalary/Build-EvidenceReceipt.ps1` | Format-only per-REQ receipt aggregator | Pure formatter over verifier objects; emits the shared golden receipt line, never re-runs evidence. Optional `-PlanDir` returns the layout-resolved `.ReceiptPath` (`assets/evidence.md`, or root `evidence.md` for legacy plans) — it resolves the path but still never writes it |
| `scripts/skalary/Test-DependencyPlan006.ps1` | Hard phase-0 dependency start-gate | Resolves the guarded plan reference and every `depends-on` token through `Resolve-Plan`; pins compatibility-anchor tokens that slimming must preserve |
| `docs/review-ledger/**` | Durable workflow-memory store by category | Seven-category taxonomy + README contract; consulted on demand, never auto-loaded |
| `scripts/skalary/Validate-Plan.ps1` + `scripts/validate.ps1` | Repo-level and single-plan entry points | Keep validation pre-approvable and composable via npm scripts. `Validate-Plan` gates on the plan's lifecycle stage: below `drafted` it prints a `PLAN-VALIDATION: SKIPPED` signal and exits 0, at or above it prints `PLAN-VALIDATION: VALIDATING` and hands the plan to `Test-Plan` unchanged |
| `docs/implementation-plans/*/assets/evidence.md` | Receipt of typed evidence checks | Source of truth for archival-gate decisions; legacy plans keep it at the plan-folder root |

## Key Patterns

| Pattern | Contract |
|---|---|
| Plan identity (naming) | Hash-plan inventory accepts both the current `<yyyy-mm-dd>-<6hex>-<slug>` grammar and the prefixed `<epic-id>-<yyyy-mm-dd>-<6hex>-<slug>` / `standalone-<yyyy-mm-dd>-<6hex>-<slug>` grammar. The folder prefix is navigational metadata only; the plan's 6-hex `plan-id` remains stable, frozen in a `<!-- plan-id: <hash> -->` header anchor, and addressable by any unique prefix ≥4 chars (git-short-SHA semantics). Legacy `NNN-<slug>` folders keep parsing in place and are never reinterpreted or renamed. Legacy ids are exactly `\d{3}`; hash prefixes are ≥4 chars, so the identity domains never overlap by length. |
| Plan-id generation | `New-PlanId` emits 6 crypto-random hex chars (ids are intentionally non-reproducible, so no slug/timestamp hashing). It scans active **and** archived ids, regenerates on a full-id collision, and warns when the id is not uniquely addressable at the 4-char minimum prefix. |
| Plan resolution | `Resolve-Plan` normalizes any reference — hash prefix (≥4), legacy 3-digit number, slug, or date — to the canonical id (the `plan-id` anchor value, or the legacy number). A non-hex reference resolves by exact slug first, then a case-insensitive **substring** match — a partial slug resolves only when it uniquely matches one plan. A 6-digit all-numeric reference is a hash, not a legacy number (length disambiguates); ambiguous prefixes/substrings error git-style. |
| User-facing plan references | In prose, questions, status reports, tables, handoffs, and recommendations, always identify a plan as `<canonical-id> <slug>` (for example, `863d97 evidence-receipt-truth`), never by id alone. Commands and machine fields may remain canonical-id-only (for example, `/ci 863d97`). Epic references follow the same `<epic-id> <slug>` display rule. |
| Typed evidence markers | Acceptance criteria use only `test:<TestId>`, `file:<path>#<assertion>`, and `review:cr|dr`. `Get-TypedEvidenceMarkers` (in `PlanState.psm1`) tokenizes every marker-shaped occurrence independently and surfaces unknown/retired prefixes verbatim, even beside known markers in one segment, so the evaluator fails loud rather than false-greening. |
| `file:` assertions | Closed vocabulary: `exists`, `contains:<regex>`, `count>=N`, `dircount>=N`. |
| Script-only validation | `cip`/`ci`/autopilot delegate validation to committed `.ps1` scripts; no in-chat or inline markdown validation logic. |
| Planning confirmation | `/cip` rephrases and confirms intent, domain/design context, and the final pre-draft summary. `planning-confirmed: pending` enrolls new plans; confirmation stores one SHA-256 digest over normalized intent and design content. Any edit makes shared state `stale`; `/ci`, `/dr`, and autopilot stop before mutation until `/cip` repeats the affected checkpoint. Marker-less historical plans remain `legacy` and proceed unchanged. |
| Read-only phase admission | Before `/ci` creates or records a worktree, repairs a plan, marks `[~]`, or initializes logs, it invokes `Get-PlanState -Json` once, surfaces state and admission from that result, and fails closed unless dependencies are complete, the first incomplete phase and its `[after:]` prerequisites are eligible, planning context can proceed, confined confirmed/legacy intent is available, and every phase `REQ-N` ref resolves through `Get-PlanMetadata`. Missing or ambiguous plan/dependency resolution, stale input, escaped plan assets, and blocked prerequisites leave the plan tree unchanged with the diagnostic cause preserved. |
| Concise vertical design | New plans scaffold a concise design with required component boundaries and Mermaid program flow; call stacks are optional. A provisional outline starts with a usable end-to-end MVP, then routes every requirement through vertical increments to the complete outcome. Objective checks own structure/routing; operator and DR own semantic usability. |
| Script distribution (bundling) | Shared state/validation/harvest scripts live once under `scripts/skalary/` and are generated into every runtime consumer. `ci` and `autopilot` both install byte-identical `Invoke-PhaseHarvest.ps1` plus `AtomicStore.psm1`, `LedgerStore.psm1`, and `PlanState.psm1`; autopilot additionally carries `Get-PhaseExecutionState.ps1`, `ReviewCycleGate.ps1`, and `Add-WorkflowNote.ps1` so container resumes do not depend on another plugin's install path. `ci`/`cip` carry their invoked validation scripts and module closure, while parser-only `pfb`/`si` consumers carry `PlanState.psm1`. SI lifecycle/schema code is the deliberate exception: it is canonical under `plugins/self-improvement/{scripts,schemas}/`; autopilot depends on that plugin and invokes its installed due writer rather than copying a foreign lifecycle script. `test:LearningLoop.PayloadOwnershipAndDrift` closes both ownership paths against manifests, dogfood, versions, scaffolds, marketplace, and registry. See plugin-registry.design.md → Skill Script Bundling. |
| Evidence receipt gating | Crosschecks rebuild the layout-resolved receipt from normalized verifier outcomes. `Test-Plan -Stage PlanCrosscheck` pure-parses that receipt and blocks missing, duplicate, undeclared, stale, failed, skipped, unrun, or degraded required markers. Only `passed` and an exact valid plan-local `waived` outcome satisfy finalization. A passed `review:cr` additionally names a durable review-run UUID and is reverified against the clean cycle, retained report/receipt pair, zero findings/non-completed tasks, and reviewed commit. |
| Phase-close checkpoint | `/ci` rereads confirmed intent, rebuilds the applicable requirement matrix from normalized evidence outcomes, and records the usable increment plus decisions/lower-impact uncertainty through `Add-WorkflowNote -Kind Capture`. Capture never resolves or downgrades uncertainty: contract, end-user experience, security, and irreversible-structure uncertainty remain high-impact blockers. Continue is available only when every outcome is passed/exactly waived and no high-impact uncertainty remains; only a recorded Continue authorizes immutable phase-harvest publication. Revise returns to evidence/checkpoint work and Stop exits without harvest; both preserve the same intent/evidence context for deterministic resume. |
| Autonomous progression | `/ci` owns runtime and execution-extent selection. Plan `scope` recommends One phase (`phase`/`step`) or Whole plan (`plan`), but the operator explicitly selects `next-phase` or `whole-plan`; missing/invalid scope recommends the bounded one-phase choice and never silently expands authority. The autopilot skill accepts that mode without a second menu, so choosing another start branch cannot alter it. Both modes invoke the same agent and admission/phase-close contract: `next-phase` stops after the first successful close, while `whole-plan` advances only after each gate passes. Operator/evidence stops preserve checklist progress for resume. |
| Validation cadence | Implementation steps run only named evidence and focused affected-surface checks. After phase work settles, phase crosscheck runs one highest-signal changed-surface Fast selection and logs its 60-second advisory target; broader coverage may be deferred rather than smuggled into "Fast." Slow and full-repository validation never run mid-phase. True plan finalization opts into complete Fast through an explicit repository parameter (`-FullRepository` here), then runs Slow once. Runtime observations never trigger an automatic repair/rerun loop. Plan text supplies typed evidence ids, never executable validation commands. |
| Review cadence and model profile | Implementation steps run focused build/test/acceptance checks without CR fan-out. After a phase, `/ci` and autopilot review the combined phase with `/cr post-phase`, selecting only the configured primary model. After every phase is complete, they run one `/cr plan-finalization` review over the whole branch with configured primary + secondary models. The role bindings, backup, reasoning effort, and context tier live only in `skills/cr/assets/model-preferences.md`. |
| Review-cycle cap | Each `phase-*` and `plan-finalization` CR stage has a durable three-cycle automatic limit, shared by interactive `/ci` and autopilot through `ReviewCycleGate.ps1`. Counts, decisions, and remediations live append-only in `cr-log.md`, so context compaction, model changes, and resumed sessions do not reset them. After cycle 3 with findings, `/ci` asks Continue looping / Wrap up; Continue authorizes one cycle only. `InvalidateContinue` is a narrow operator repair: it requires authorization and reason, targets the exact unique latest Continue by persisted-line SHA-256, records UTC time, and is rejected after any later result/event or for stale, duplicate, ambiguous, missing, or wrong-stage targets. A valid invalidation restores `operator-decision` for the same cycle so ordinary Wrap remains the truthful terminal choice; it cannot rewrite history or bypass evidence/review gates. Autopilot logs findings, commits the in-progress state, and exits 42 for that operator decision. |
| Ledger dedup-key contract | `Add-LedgerEntry.ps1` keeps two keys: idempotence key (`category + normalized-lesson + plan + src + severity + sorted-tags`, date excluded) and recurrence key (`category + normalized-lesson + sorted-tags`, plan/src/date excluded). |
| Ledger plan-id compatibility | The `$Plan` validator accepts `[0-9a-f]{4,6}` hash prefixes and `<yyyy-mm-dd>` dates alongside `\d{3}` (so `Resolve-LedgerPlanId` can fold any reference before writing), while the `ConvertTo-LedgerRecord` parse regex and the written entry string stay strictly `[0-9a-f]{6}` or `\d{3}`. Widening the parser rescues previously-unparseable well-formed `plan-<6hex>` entry lines so they survive append + canonical rewrite. The canonical rewrite reconstructs the file from the leading header block plus parseable `\d{3}`/`[0-9a-f]{6}` entry lines only — interleaved free-form or malformed lines placed after the first record are not preserved. The reference is folded to one canonical id via `Resolve-Plan` before any key is built, so dedup/recurrence keys never fork across schemes; only `[0-9a-f]{6}` or `\d{3}` is ever written. |
| Shared receipt grammar | `Build-EvidenceReceipt.ps1` is the single emitter of the golden per-REQ line `<glyph> REQ-N — <marker> — <result> — <commit>` (em-dash `U+2014` with surrounding spaces; `✓ U+2713` passed, `⊘ U+2298` waived, `✗ U+2717` every other outcome; optional `: <note>`). The closed result vocabulary is `passed`, `failed`, `skipped`, `unrun`, `stale`, `degraded`, and `waived`; legacy `Success` inputs are normalized without relabeling non-passes. A REQ passes only when all markers are passed or exactly waived. The formatter never executes evidence. |
| Plan-local evidence waivers | A current-layout plan may carry optional `assets/evidence-waivers.json` (legacy layout: `evidence-waivers.json`) with schema `skalary/evidence-waivers@1`. Each closed entry binds the canonical plan id, exact REQ, exact declared marker, source outcome `skipped` or `degraded`, bounded reason, and optional `Windows`/`Linux`/`MacOS` platform. Wildcards, wrong-plan/REQ/marker bindings, duplicate bindings, malformed reasons, and waivers for failed/unrun/stale evidence are rejected. The receipt visibly renders the derived status as `waived`, and PlanCrosscheck revalidates the exact binding and reason. |
| Focused test evidence | `Run-UnitTests.ps1` remains the only Pester executor. Focused Fast callers may pair `-EvidenceTestId <id[]>` with `-EvidenceResultPath <json>` and explicit `-TestPath`; IDs bind exact leading `test:<id>` tokens after the ordinary one-pass discovery/run. The `skalary/evidence-test-results@1` output preserves per-ID selected/executed counts and maps pass, fail, skip, mixed pass/skip, missing match, not-run, discovery error, and interruption to the shared outcomes. Any non-pass keeps the runner red; callers feed the structured records to the formatter so an exact waiver can be evaluated without claiming the run passed. |
| Receipt freshness ordering | The builder binds full `HEAD`. Finalization writes the receipt and runs PlanCrosscheck before committing. A subsequent commit may retain the parent source only when that commit changes the receipt and nothing else; any implementation, plan, policy, review, or mixed commit makes the persisted receipt stale and requires rebuilding. This narrow receipt-only exception prevents the act of persisting proof from invalidating itself without introducing a second digest protocol. |
| Workflow-memory capture | Mid-run writes are script-mediated via `Add-WorkflowNote.ps1` with exactly three layout-resolved kinds: `CrLog` for review findings, `Learnings` for the closed trigger set, and `Capture` for usable increments, decisions, uncertainty, and checkpoint dispositions. No checkpoint-specific file, parser, or authority exists. Entries carry closed concern/review types, plan-validated sorted REQ ids, and kind-domain-separated source-record ids. The 10-entry active cap is **Learnings-only**; overflow is persisted first as an append-only content-addressed batch, while old summary lines are retained and reported as `legacy-loss`. `CrLog` and `Capture` are uncapped. |
| Planning capture compatibility | Planning/interview history may occupy a `Phase: 0` Capture section. Phase harvest accepts phase zero for durable close proof, selects typed records only from Capture, and permits only generated empty placeholders in phase-zero CR and learning sections; later executable phase records remain independently reachable. |
| Phase-harvest replay trust | Native `phase-harvest-receipt/v2` receipts carry the exact typed source record for every candidate. `Invoke-PhaseHarvest -ValidateReceipt -Phase N` exposes the same closed, read-only validation used by replay so launchers never treat file existence as phase-close proof. Validation checks the envelope, digest, repo/plan/phase identity, status, bounded sources, and byte-stable candidate re-derivation before a completed phase may be skipped. A committed v1 close can enter this contract only through explicit `Invoke-PhaseHarvest -MigrateLegacyReceipt -Phase N -SourceRef HEAD`: the command performs no harvest or ledger mutation, requires clean tracked plan/receipt/source paths and a source ref equal to current HEAD, finds the unique path-specific commit that introduced the exact v1 blob, verifies its tree, enumerates the complete conventional log and overflow source set from that tree, and requires exact source/candidate re-derivation. The replacement is written under the shared harvest lock with a generation check. It remains schema v2 but carries a content-addressed `phase-harvest-receipt-migration/v1` envelope binding UTC migration time, tool identity, original v1 receipt/payload hashes, source blob/commit/tree/ref/path, and recomputed validation results. Validation and replay always reconstruct the v2 payload from those immutable objects and require an uninterrupted Git path history whose migration commit directly replaced the declared v1 blob; missing history, altered provenance, omitted records, intervening receipts, ambiguity, or any disagreement fails closed. An identical migrated receipt is idempotent, while native/conflicting v2 is never overwritten. The active source path remains authoritative after the plan folder moves under `archived/`. Unmigrated v1 remains rejected by active replay and readable only by SI history ingestion; SI accepts the migration envelope only after its own closed metadata/digest check and still re-derives every v2 candidate. Repository-local identities are path digests, never committed absolute paths; ledger consumers treat all entry prose as untrusted data. |
| Shared writer durability | `AtomicStore.psm1` is root-canonical and bundled by import closure into PFB, CI, CIP, SI, and autopilot. Feedback, workflow-note, ledger, and SI state writers share its repo-scoped lock, generation digest, same-directory random text/byte temp, validation hook, atomic replace, three-conflict retry, and closed `complete` / `lock-timeout` / `cas-conflict` / `cas-exhausted` / `capacity-blocked` / `invalid` status vocabulary. Byte-mode replace preserves corrupt recovery artifacts without a decode/re-encode round trip. |

## Design Decisions

- An epic indexes sibling plan folders instead of nesting them. Nesting would have forced every consumer — inventory, resolver, validator, ledger, archival — to learn a second folder shape, and would have made "independently executable child plan" structurally false. Indexing keeps the child a plain plan and confines epic knowledge to `New-Epic` + the rollup.
- Epic decomposition context is duplicated into each child deliberately. `epic.md` remains the goal-level index, but a child may be drafted weeks later and must stand alone; storing only the accepted cut in chat or the epic makes the child handoff lossy. `/cep` owns the preliminary provenance and decomposition decisions, while `/cip` owns confirmation and full drafting.
- The epic's child table is derived state, rebuilt from the markers on disk on every run, including for the epic a `-Force` re-parent moved a child *away* from. A mirror that is only refreshed for the invocation target is a second source of truth that goes stale exactly when membership changes.
- A plan reference keeps winning over an epic reference in `Get-PlanState`. Both resolvers accept fuzzy date and slug forms, so preferring epics would break references that already resolved to a plan; hex ids are unique across both spaces, so `/ci <epic-id>` still lands in epic mode and `-Epic` forces the fuzzy forms.
- Plan parsing lives in `PlanState.psm1` so `Test-Plan.ps1`, `New-Plan.ps1`, and the state CLI share one parser. `Get-PlanMetadata` takes an explicit `-RepoRoot` parameter (it previously closed over a script-scoped variable, which a module function cannot inherit under `Set-StrictMode`); all call sites pass it and parity is proven under a non-default `-RepoRoot`. `Get-TypedEvidenceMarkers` also lives here (the shared parser) so the closed marker vocabulary and its fail-loud-on-unknown-prefix behavior are single-sourced.
- The plan layout resolver lives in `Get-PlanMetadata`, not at the `Test-Plan` call boundary. `Get-PlanMetadata` builds `.Requirements` / `.Risks` / `.Decisions` for every consumer, so resolving only at the validator would leave `Get-PlanState` and `Get-NextStep` with zero requirements the moment a plan migrated. Resolution is **per section**, not per plan: an `assets/` folder holding no recognized files falls back section-by-section rather than switching the whole plan into a broken mode.
- Empty and malformed assets fail loud instead of falling back. A silent fallback would turn a truncated `assets/requirements.md` into "this plan has no requirements", which greens every REQ gate. `New-Plan` therefore scaffolds placeholders with real content so "present-but-empty" stays distinguishable from "authored".
- Migrating a plan to the assets layout must be a single atomic edit — write the asset files and remove the in-`plan.md` tables together, then re-validate before committing. `/ci` picks the first incomplete step in document order and re-parses the plan between steps, so a committed half-state would be mis-parsed by the very next `Get-PlanMetadata` call. `test:migration-is-atomic` asserts no plan folder is left with neither a legacy table nor its asset.
- Plan ids are random, not content-derived: a hash of slug/timestamp adds no recoverable meaning when ids are non-reproducible by design, so `New-PlanId` uses crypto-random hex and resolves collisions by scanning the active + archived inventory. `Repair-Plans` (and any migration) must never mutate an existing `plan-id` anchor.
- A plan's id is written into the ledger and `depends-on:` in exactly **one** canonical form; callers resolve any reference to that canonical form via `Resolve-Plan` before writing, so dedup/recurrence keys never fork across the legacy/hash schemes. The `Test-DependencyPlan006` start-gate resolves both the guarded reference and each declared dependency the same way, so a legacy `006` and a hash-style dependency trigger identical preflight behavior.
- Ledger hash-id compatibility preserves **well-formed** entry lines: widening the parser (validator + `ConvertTo-LedgerRecord` regex + entry string) was co-edited so previously-unparseable `[0-9a-f]{6}` entry lines become records and survive the canonical rewrite instead of being silently dropped. The rewrite reconstructs from the leading header + parseable records, so it does not guarantee retention of interleaved comments or malformed/short-hex lines placed after the first record; a mixed-format round-trip regression test guards the entry-line case.
- Evidence receipts have one golden grammar emitted only by `Build-EvidenceReceipt.ps1`; orchestrators and autopilot consume that shared formatter rather than hand-writing receipt lines, so the receipt shape stays identical across `ci`/`cip`/autopilot. Its module imports reuse loaded plan modules instead of force-reloading them, because an in-process invocation must not remove `PlanState` commands from its caller's scope. Evidence readers emit flat record streams so multi-marker receipts and waiver sets are checked entry by entry rather than collapsing into one aggregate record. The persisted receipt is not trusted merely because it exists: `Test-Plan -Stage PlanCrosscheck` re-derives marker coverage, freshness, and exact waiver validity before finalization.
- The workflow scripts have a single source of truth (`scripts/skalary/`) but are duplicated into each consuming plugin rather than shared through a runtime module or a common plugin. Plugins install and are versioned independently, so a shared runtime location cannot guarantee a compatible script is present; managed duplication (generated by `Sync-PluginScripts.ps1`, drift-gated to byte-identical) is the accepted cost of that independence. Consequently, **a change to any shared script bumps the `version` of every plugin that bundles it** — the edit is a payload change to each dependent plugin.
- `Test-Plan.ps1` is the single validation authority so approval/allowlist models stay stable across host/container/autopilot execution.
- The `human-step-detail` gate is exempted for archived plans rather than blanket-warn or retro-fitted. `scripts/validate.ps1` validates every plan file including `docs/implementation-plans/archived/`, and existing archived plans predate the gate; making the gate advisory everywhere would leave the requirement unenforced, while editing archived plans would rewrite history to satisfy a rule that did not exist. `IsArchived` is derived from the plan's own resolved path (an `archived` folder directly under `implementation-plans`), not from `-RepoRoot`, which may be relative and would resolve against the wrong base.
- Step detail is captured from the **raw** plan lines rather than the fence-stripped copy used for structural parsing. `@human` handoffs routinely carry fenced operator commands, and capturing the stripped copy would silently hand the operator prose with the commands blanked out — the exact failure the gate exists to prevent.
- Stage-aware validation avoids self-blocking plans during drafting while still enforcing strict verification at crosscheck/finalization.
- Plan lifecycle stages are a **closed, ordered set** defined once in `PlanState.psm1` (`scaffolded` < `drafted` < `dr-round-<n>` < `done`). Any reader that treats "not `drafted`" as "skip validation" turns a typo into a pass that exits 0 while checking nothing, so an unrecognised value throws instead of resolving to a skip, and `Set-PlanStage` rejects it at write time. Two deliberate asymmetries: a **missing** anchor resolves to `drafted` (older plans keep being validated exactly as before), and a caller-supplied floor is ranked against the family list so every value `Get-PlanStageOrder` publishes is a usable floor — a bad floor blames the caller, a bad anchor blames the plan.
- Evidence is machine-checkable only; non-deterministic markers (`cmd:`/`manual:`) are excluded to preserve autopilot safety and repeatability.
- A skipped validation announces itself, and there is only one floor. `npm test` validates plans twice — `Validate-Plan.ps1` for the working plan, `scripts/validate.ps1` for the whole tree — so both call `Get-PlanValidationDecision` and print the `PLAN-VALIDATION: SKIPPED …` / `PLAN-VALIDATION: VALIDATING …` signal it returns. A floor honoured by only one leg would be cosmetic: the below-floor plan is skipped by one and hard-failed by the other, changing nothing but which leg reports it. Exiting 0 with no signal is equally useless, because a silent skip is indistinguishable from a pass to anything reading the exit code. Default plan resolution resolves the stage of **every** candidate, so a plan carrying a bad marker fails on the spot instead of waiting until it happens to be selected.
- Workflow-memory mutation is script-only (`Add`/`Remove`) and invoked through bound argument arrays; orchestrators do not hand-edit ledger files.

## Constraints

- Plan text is untrusted input. Validation scripts must use pure parsing/bound parameters (no dynamic command execution from plan content). New-plan slug input is sanitized to `[a-z0-9-]` and canonicalize-then-confined under `docs/implementation-plans`.
- Plan identity is dual-format: legacy `NNN-<slug>` folders keep parsing and stay in place; hash plans may use either the current `<date>-<hash>-<slug>` grammar or the prefixed `<epic-id|standalone>-<date>-<hash>-<slug>` grammar. The `plan-id` anchor is the canonical id and is never rewritten by migration.
- New scaffolds write a final consistent prefix directly: an epic child's six-hex folder prefix equals its canonical `epic` marker, while a direct plan uses `standalone` and has no epic marker. Migration rejects source identity or membership mismatches before moving anything. Inventory still resolves both hash grammars by `plan-id` so a navigational prefix never becomes identity, including during mixed-layout rollout and later re-parenting.
- Epic index folders remain unprefixed as `<date>-<epic-id>-<slug>` under `docs/implementation-plans/epics/`; only plan folders gain the navigational prefix.
- A legacy `NNN-<slug>` folder must not carry a divergent hex `plan-id` anchor: `Get-PlanInventory` sets the canonical id to the anchor value when present, so a mismatched anchor makes the plan unaddressable by its 3-digit number and can fork ledger/`depends-on` keys.
- Header anchors (`plan-id`, `cip-stage`) are read/written file-wide today (`Get-PlanInventory`, `Set-PlanStage`), not header-scoped like `Get-PlanHeaderMarkers`. Keep these anchors in the pre-`##` header and never place an example `<!-- plan-id: ... -->` / `<!-- cip-stage: ... -->` in the body — a body occurrence can hijack canonical identity or block the real stage write.
- `Get-PlanState`'s uncommitted-changes probe fails closed: a `git status` launch or exit failure aborts state/admission instead of misreporting a clean tree. Callers with an already-authoritative worktree result may bind `-HasUncommittedChanges` explicitly.
- Legacy plans without `<!-- evidence: required -->` run in warn-only mode for strict integrity classes; opted-in plans enforce blocking behavior.
- Log and receipt paths are layout-dependent. Any new writer or reader of a plan-folder file must resolve through `Resolve-PlanAssetPath` (or a script that does); hard-coding either the `assets/` or the legacy root path reintroduces the split-brain REQ-20 exists to prevent.
- Any workflow change that alters marker grammar, stage semantics, completion gates, or the plan naming/id scheme must update this note and the relevant `cip`/`ci` assets in the same change.
- Any edit to a `scripts/skalary/` script that is bundled into a plugin must re-run `Sync-PluginScripts.ps1` (which re-copies the bundle and **patch-bumps the `version` of every plugin that bundles that script**), then rebuild `registry.json`, in the same change; the `Sync-PluginScripts.ps1 -WhatIf` bundle drift gate in `scripts/validate.ps1` fails CI otherwise.
